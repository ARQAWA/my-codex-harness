# Scope Focus: концепция и решения

Этот документ объясняет назначение Scope Focus и причины решений в его
рабочих skills. Предложения, решения пользователя и фактические изменения
различаются. Текущий порядок работ хранится в достаточном первичном источнике
или в todo-списке Main. Действующие правила записаны в `AGENTS.md`, `WORKFLOW-MANIFEST.md`, skills и
профилях; прежние версии доступны в истории Git.

## Назначение

Scope Focus делает из Codex harness по `WORKFLOW-MANIFEST.md`: агент работает
как владелец — быстро, просто и итерациями, делает всё согласованное и ничего
сверх него. Root Main ведёт todo-список для любой задачи, кроме одного
ответа или одного короткого действия, и сам ставит native Goal для задачи из
нескольких зависимых этапов. Перед работой с изменениями, кроме micro, Main
спрашивает пользователя только о неоднозначной формулировке и о собственных
решениях сверх его слов. Review запускается автоматически по классу, который
Main определяет сам: micro — без проверки, small проверяет Spotty, large —
Smarty; ответ или запрошенный файл-отчёт без правок проекта и настроек review по классу не
запускается; `$define-goal` записывает класс в цель. Gate финализации идёт только при release; аудит
Bossy — при release раз в неделю или по прямой просьбе владельца. Это действующий текстовый контракт, не доказательство
runtime-надёжности.

`gold-standard` возвращает внимание агента к принципам выбора и исполнения
решения: полный качественный результат самым простым, коротким, быстрым и прямым
способом, с минимальным достаточным изменением и без лишней механики.

## Золотой стандарт и коммуникация

Владелец согласовал Золотой стандарт с публичным вызовом `$gold-standard`
и автоматической подачей root Main. Skill описывает способ работы владельца:
кратчайший путь с минимумом нужных сведений, тяжёлая работа только по приказу,
проверка чтением и остановка после результата. Системный промпт Codex —
RC2 из my-omp-harness, перенесённый под Codex, с моделью GPT Model и
четырьмя уточнёнными абзацами об удержании задачи из `SYSTEM.md`, коммит `436aa2e`;
правила todo-списка, Goal, review и субагентов поступают только из плагина и в
промпт не переносятся.
Разделы о личности, стиле речи и оформлении PR в стандарт не переносятся. Skill самодостаточен и не читает рабочий репозиторий.
Явный вызов доступен для повторного применения; `allow_implicit_invocation: false`, текст подаёт hook;
сам вызов не требует отдельного отчёта, чек-листа или дополнительного workflow.

Согласованное удаление, замена или переделка включает удаление связанных
устаревших исходников, конфигурации, документации, ссылок и прочих частей
в затронутой области. Отключённые ветки, закомментированный код, ненужные
compatibility-слои, архивные копии и записи об отмене ради сохранения прошлого
не остаются; история хранится в Git. Это не разрешает общий cleanup, удаление
пользовательских данных, чужой работы, необходимых доказательств или поведения,
которое остаётся обязательным. Сведения о действующем решении сохраняются.

`clear-communication` задаёт русский язык, главное в первой жирной фразе и
формат ответов и вопросов. Частоту, содержание и длину промежуточных сообщений
задаёт выбранный системный промпт; skill разрешает кратко объяснять работу и
план, когда промпт требует такого обновления. `codex-tools` запрещает пересказ
сырого вывода инструментов, не запрещая сами обновления. Длительное ожидание
объясняется один раз.

`$define-goal` начинает работу после пересказа цели без дополнительного «го»,
если пересказ не содержит вопросов, собственных предложений или отклонений,
которые требуют решения владельца. При наличии таких вопросов Main ждёт
подтверждения; итоговый review по классу работы сохраняется.

`hooks/communication.cjs` читает источники из установленного пакета, без
встроенных копий. `SessionStart` с startup/resume/clear/compact подаёт root
Main Gold Standard, `codex-tools` с путём CLI чтения, `main-workflow`,
`subagents` и Clear Communication; `SubagentStart` подаёт субагенту только
`codex-tools` с путём CLI чтения. У `SessionStart`
`additionalContextLimit = 65536`, подача Main занимает около 43 КБ; у
`SubagentStart` 32768. Подача
действует при включённом пакете и native trust текущих hooks и не гарантирует
следование модели. Hook ничего не записывает. Изменение исходников не означает
release, push или обновление runtime-копий.

По решению владельца 2026-10-11 сообщение Main начинается с
жирного предложения с главным, обычный ответ — один абзац из 1–4 коротких
предложений, максимум 12, а причины, ход работы и варианты даются только по
просьбе или при согласовании. Вопросы идут в чате в формате «Вопросы · N» с
вариантами буквами и рекомендованным вариантом; карточки
`request_user_input_async` не используются.

## 2026-10-16: возврат потерь переноса

Владелец заметил, что установленный Main отказывается запускать агентов вне
пяти профилей, и поручил: «Надо все потери найти и вернуть их на место».
Причина отказа: в omp рядом с запретом стоял пункт `custom` для агента на
названной пользователем модели, а при переносе в skill `subagents` остался
один запрет запускать агентов вне пяти профилей. Сверка с `my-omp-harness` и состоянием репозитория до
переноса нашла ещё потери. На три вопроса владелец ответил «1а 2a 3b».

Выполненное изменение:

- `subagents`: список профилей не ограничивает пользователя; названные им тип
  агента, роль, модель и reasoning Main запускает как есть, без своих агентов;
  профиль закрепляет модель и reasoning, пока пользователь их не назвал.
- `codex-tools`: возвращены правила скорости старого промпта Codex и
  `omp-tools` в форме Codex: скорость выше числа ходов, независимые вызовы
  вместе, широкий поиск одним паттерном, чтение вместо догадок, без пересказа
  вывода и повторного чтения после патча. Удалено требование стирать
  временный скрипт: временные файлы не удаляют.
- `AGENTS.md`: возвращены заморозка форка Codex CLI и патча VS Code Extension
  (не читать, не искать и не менять) и правило не переносить прежние многократные review и
  cleanup в каждый запуск.

## 2026-10-16: согласование только по делу

Владелец пожаловался, что Main планирует и просит «go» на каждую мелочь. Решение
найдено в истории omp: сессия 01a130bc, жалоба «Он должен согласовывать со мной
только те места, которые однозначно являются неоднозначными. Там, где reviewer не
сможет провести нормальное review, не сможет подтвердить результат работы, потому
что формулировка неоднозначная. Или он согласовывает со мной решения, которые он
придумал самостоятельно, которые отличаются от того, что я ему сказал сделать.»,
одобрение «1a go».

Выполненное изменение по тексту этого решения:

- `main-workflow`: шаг согласования вместо шага требований. Main спрашивает только
  о формулировке, по которой ревьюер не подтвердит результат, и о своих решениях
  сверх слов пользователя, с предложением, причиной и вариантами; остальное
  начинает сразу. Список требований, класс и вопрос «go» в чат не идут, класс Main
  определяет сам. Ответ или запрошенный файл-отчёт без правок проекта и настроек review по
  классу не запускается.
- Согласие для ревьюера — слова пользователя, его ответы и принятые им
  предложения: так сказано в `blind-review-cycle`, профилях Spotty, Smarty и
  Bossy и в `WORKFLOW-MANIFEST.md`.
- `gold-standard`, `clear-communication`, `define-goal`, `AGENTS.md` и
  `install-instructions/scope-focus.md` приведены к этому правилу.
- `main-workflow` и `define-goal`: цель не получает лимит токенов и создаётся в
  том же ответе, что и первая работа; вызов todo CLI тоже идёт в одном ответе с
  работой. Так в одобренных пунктах «Цель без лимита» и «Todo и goal Main будет
  вызывать в тех же ходах, что и основную работу».
- `WORKFLOW-MANIFEST.md`: фраза про дифф за диффом и подтверждение требований
  заменена правилом о вопросах только по открытым местам; в omp владелец одобрил
  эту правку манифеста своим «1a go».

Остальные правки одобренного решения держатся на расширениях omp (волны
explorer, подача ответа субагента, схемы служебных инструментов и вызов цели через
шлюз `eval`) и в Codex не переносились. `$define-goal` и Plan mode со своим согласованием не менялись.
Release и установка не выполнялись.

Владелец поручил: «Мы переносим наш to-do плагин, to-do extension в Codecs.», согласился с переносом только механики («Похуй на визуал, без него заебись. Она ведётся через хуки и наш кастомный tooling. Агент вызывает наш кастомный tooling, через него пишет сам в определённые файлы, пишет эти данные, и из этих файлов они инжектятся в контекст модели. Выполненное изменение:

- `tools/todo.cjs`: порт `todo.ts` из omp на Node.js, без панели. Те же операции (`init`, `append`, `start`, `done`, `drop`, `block`, `unblock`, `rm`, `plan`, `step`, `closed`), статусы, адресация пунктов по номеру или тексту, снимок `<todo>` и напоминание `<todo-reminder>`. Агент вызывает CLI через shell с JSON `{"ops":[...]}`; сессию CLI узнаёт по `CODEX_THREAD_ID`, список лежит в `<CODEX_HOME>/scope-focus-todo/todo-<id сессии>.json`.
- `hooks/todo.cjs` и записи `UserPromptSubmit` и `Stop` в `hooks/hooks.json`: `UserPromptSubmit` подаёт снимок, а когда открытых пунктов нет, напоминание; `Stop` один раз за ход (`stop_hook_active`) возвращает модель к работе, пока есть пункты `pending` или `in_progress`, текстом причины из omp; `blocked` ход не держит. - `main-workflow` (раздел «The todo list»), `install-instructions/scope-focus.md` и `AGENTS.md` описывают todo CLI и четыре hooks; `clear-communication` называет пункты списка вместо шагов плана.

CLI и hooks проверены пробными вызовами во временном `CODEX_HOME`; `CODEX_THREAD_ID` в shell модели совпадает с `session_id` rollout в живом `codex exec`. Проверка формата ответа субагентов (`SubagentStop`) в этот перенос не входит.

## Сессионная память решений и восстановление истории

Владелец поручил перенести decisions из My OMP Harness в Codex: «чтобы кодекс
помнил всё, что мы решали, все решения, которые мы приняли в течение сессии».
Для старых чатов: «Он сначала прогоняет его через decision, собирает базу и
подкладывает её в контекст, а потом скиллом вызывает сборку to-do».
Модель выбрана прямо: «GPT 6-1 sol с effort low без хайку вообще».

Реестр решений отделён от плана работы. Он хранит слова владельца, явно
принятые предложения, замены и отмены; область действия решения сохраняется.
Согласие на прежнюю задачу не становится разрешением выполнять новую.
Факты о проделанной работе используются при восстановлении todo, но не
превращаются в решения владельца.

Один recorder `gpt-6.1-sol / low` без предварительного фильтра вызывается
`UserPromptSubmit` через `tools/decisions.cjs`. Штатный `codex exec`
использует действующие вход и конфигурацию, отключает hooks и plugins и
работает во временном каталоге в read-only sandbox. Ошибка блокирует подачу
сообщения. JSON сессии хранится в
`<CODEX_HOME>/scope-focus-decisions`, CLI выводит его в читаемом виде с
цитатами и источниками. Root Main получает решения на старте,
при resume и compaction и после нового сообщения; субагентам Main передаёт
только нужные решения в брифе.

`$restore-session` последовательно пересобирает решения из сохранённых
исходных rollout через `tools/session-history.cjs`, включая сообщения до
compaction, подаёт собранную базу в контекст Main и вызывает `$restore-todo`.
Main читает все страницы истории,
сопоставляет решения, факты и выполненную работу и восстанавливает только
оставшиеся согласованные задачи. Оба этапа используют один неизменяемый снимок
исходной истории на момент запуска; новые tool outputs восстановления не
становятся бесконечно растущим входом. Источник и покрытие записаны в реестре,
промежуточный кандидат replay не заменяет действующие решения до завершения.
Для истории больше контекста рабочая
сводка с источниками и курсором сохраняется во временной папке ОС.
Восстановление не запускает задачи. Если исходные сообщения отсутствуют,
пересказы не считаются доказательством полного восстановления.
