# Scope Focus: концепция и решения

Этот документ объясняет назначение Scope Focus и причины решений в его
рабочих skills. Предложения, решения пользователя и фактические изменения
различаются. Текущий порядок работ хранится в достаточном первичном источнике
или в плане `update_plan`. Действующие правила записаны в `AGENTS.md`, `WORKFLOW-MANIFEST.md`, skills и
профилях; прежние версии доступны в истории Git.

## Назначение

Scope Focus делает из Codex harness по `WORKFLOW-MANIFEST.md`: агент работает
как владелец — быстро, просто и итерациями, делает всё согласованное и ничего
сверх него. Root Main ведёт план `update_plan` для любой задачи, кроме одного
ответа или одного короткого действия, и сам ставит native Goal для задачи из
нескольких зависимых этапов. Перед работой с изменениями, кроме micro, Main
подтверждает у пользователя проверяемые требования и класс работы. Review
запускается автоматически по классу: micro — без проверки, small проверяет
Spotty, large — Smarty; `$define-goal` записывает класс в цель. В Codex Plan
mode идут две проверки Spotty. Gate финализации идёт только при release; аудит
Bossy — при release раз в неделю или по прямой просьбе владельца. Это действующий текстовый контракт, не доказательство
runtime-надёжности.

`gold-standard` возвращает внимание агента к принципам выбора и исполнения
решения: полный качественный результат самым простым, коротким, быстрым и прямым
способом, с минимальным достаточным изменением и без лишней механики.

## Золотой стандарт и коммуникация

Владелец согласовал Золотой стандарт с публичным вызовом `$gold-standard`
и автоматической подачей root Main. Skill описывает способ работы владельца:
кратчайший путь с минимумом нужных сведений, тяжёлая работа только по приказу,
проверка чтением и остановка после результата. Системный промпт Codex содержит
только общие правила поведения и не ссылается на плагин; правила плана, Goal,
review и субагентов поступают только из плагина и в промпт не переносятся.
Разделы о личности, стиле речи и оформлении PR в стандарт не переносятся. Skill самодостаточен и не читает рабочий репозиторий.
Явный вызов доступен для повторного применения; `allow_implicit_invocation: false`, текст подаёт hook;
сам вызов не требует отдельного отчёта, чек-листа или дополнительного workflow.

Согласованное удаление, замена или переделка включает удаление связанных
устаревших исходников, конфигурации, документации, ссылок и прочих частей
в затронутой области. Отключённые ветки, закомментированный код, ненужные
compatibility-слои, архивные копии и записи об отмене ради сохранения прошлого
не остаются; история хранится в Git. Это не разрешает общий cleanup, удаление
пользовательских данных, чужой работы, необходимых доказательств или поведения,
которое остаётся обязательным. Сведения о действующем решении сохраняются.

`clear-communication` сохраняет короткую связную речь и понятное практическое значение;
причины даются только по просьбе или при согласовании. Промежуточные сообщения нужны при существенном
результате, изменении подхода, важной неопределённости, блокере или необходимости
ответа пользователя. Небольшие наблюдения объединяются. Короткая задача не требует
вступления; для продолжительной работы оно объясняет существенный объём или
ожидаемую задержку. Длительное ожидание объясняется один раз, затем сообщаются
изменения либо ответ на запрос статуса. Чтение, поиск, команда, выбор или
автозагрузка skill и прошедшее время сами по себе сообщения не требуют.
Обязательные вопросы, согласования и раскрытие реальных ограничений сохраняются.
Правила финального ответа сохранены дословно.

`hooks/communication.cjs` читает источники из установленного пакета, без
встроенных копий. `SessionStart` с startup/resume/clear/compact подаёт root
Main Gold Standard, `codex-tools` с путём CLI чтения, `main-workflow`,
`subagents` и Clear Communication; `SubagentStart` подаёт субагенту только
`codex-tools` с путём CLI чтения. У `SessionStart`
`additionalContextLimit = 65536`, подача Main занимает около 39 КБ; у
`SubagentStart` 32768. Подача
действует при включённом пакете и native trust текущих hooks и не гарантирует
следование модели. Hook ничего не записывает. Изменение исходников не означает
release, push или обновление runtime-копий.

По решению владельца 2026-10-11 сообщение Main начинается с
жирного предложения с главным, обычный ответ — один абзац из 1–4 коротких
предложений, максимум 12, а причины, ход работы и варианты даются только по
просьбе или при согласовании. Вопросы идут в чате в формате «Вопросы · N» с
вариантами буквами и рекомендованным вариантом; карточки
`request_user_input_async` не используются.

## 2026-10-15: перенос концепции my-omp-harness

Владелец поручил: «Посмотри май омп хайрнес и на базе него подумай как
переделать my codex harness и дай обоснование». Предложение из десяти пунктов
он принял словами «го реки все делай»; на три вопроса ответов не было, поэтому
взяты рекомендованные варианты: вопросы в чате, как в omp; `enot` удалить;
`code_writer` и `shell_runner` на `gpt-6-luna / medium`. Причина по принятому предложению: с одним ядром, `WORKFLOW-MANIFEST.md`,
сверяется всё остальное; при расхождении меняется остальное, а манифест
остаётся.

Выполненное изменение:

- Добавлен `WORKFLOW-MANIFEST.md` — ядро harness по тексту omp с механикой Codex.
- `new-model-instructions.md` заменён коротким промптом omp `SYSTEM.md`:
  личность, стиль, работа с пользователем, skills. Правила стандарта,
  инструментов и общения он не повторяет.
- Gold Standard, `clear-communication`, три review-цикла, `subagent-brief`
  перенесены из omp; новые skills `main-workflow` (шаг требований, классы
  micro/small/large, план `update_plan`, native Goal, две проверки Spotty в
  Plan mode), `subagents` и `define-goal` (`$define-goal`).
- Hook подаёт root Main Gold Standard, `codex-tools`, `main-workflow`,
  `subagents` и Clear Communication, субагенту — только `codex-tools`.
- Spotty, Smarty и Bossy получили общий промпт omp с находками на дословных
  цитатах; модели `gpt-6.1-sol` low, medium и high сохранены. Добавлены
  профили `code_writer` и `shell_runner`, запуск с `fork_turns: "none"`.
- Удалены Lunatron целиком, `enot`, ToSpec, skill `goal`, Task Notebook,
  `cleanup-task`, `cleanup-notebook` и спецификации в `specs/`. Следы
  Lunatron, Task Notebook и ToSpec на хосте убирает `LEGACY-CLEANUP.md` по
  отдельной просьбе, а устаревший профиль `enot` — шаг обновления установки.
- `finalize-work` и новый `repo-audit` по образцу omp: при release сверка
  установленных копий и документации diff, CLEAN класса переиспользуется,
  недельный аудит Bossy с тегом `audit`; работа в ветке и worktree задачи со
  squash-слиянием при release.

Механика Codex — `apply_patch`, `exec`, CLI чтения, hooks, TOML-профили,
cachebuster — сохранена. Установка и release не выполнялись.

## 2026-10-16: возврат потерь переноса

Владелец заметил, что установленный Main отказывается запускать агентов вне
пяти профилей, и поручил: «Надо все потери найти и вернуть их на место».
Причина отказа: в omp рядом с запретом стоял пункт `custom` для агента на
названной пользователем модели, а при переносе в skill `subagents` остался
один запрет запускать агентов вне пяти профилей. Сверка с `my-omp-harness` и состоянием репозитория до
переноса нашла ещё потери. На три вопроса владелец ответил «1а 2a 3b».

Выполненное изменение:

- `subagents`: список профилей не ограничивает пользователя; названные им тип
  агента, роль, модель и reasoning Main запускает как есть, без своих агентов;
  профиль закрепляет модель и reasoning, пока пользователь их не назвал.
- `codex-tools`: возвращены правила скорости старого промпта Codex и
  `omp-tools` в форме Codex: скорость выше числа ходов, независимые вызовы
  вместе, широкий поиск одним паттерном, чтение вместо догадок, без пересказа
  вывода и повторного чтения после патча. Удалено требование стирать
  временный скрипт: временные файлы не удаляют.
- `AGENTS.md`: возвращены заморозка форка Codex CLI и патча VS Code Extension
  (не читать, не искать и не менять) и правило не переносить прежние многократные review и
  cleanup в каждый запуск.
