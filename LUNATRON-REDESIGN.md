# Проект переработки Lunatron

Это согласованный проект и TODO-план с последними поправками владельца.
Текущий заказ — разработка исходников, проверка, затем commit и push.
Установка в runtime запрещена этим заказом.

## 1. Роли и границы работы

Цель — освободить Main от массового чтения, выполнения команд и генерации
элементарного кода. Main сохраняет сложную интеллектуальную работу и отвечает
перед пользователем за весь результат.

| Роль | Работа | Граница полномочий |
| --- | --- | --- |
| **Main** | Анализ, архитектура, решения, написание и прямое применение собственных сложных патчей, точечное чтение оригиналов, итоговая приёмка и ответ пользователю. | Не читает большие массивы. Рабочие команды, включая короткие, и простые изменения выполняет Lunatik. |
| **Lunatik** | Выполняет точные команды и простые патчи Main; пишет только элементарный код по конкретному образцу; сообщает Main о готовности порученной работы. | Не придумывает структуру, алгоритм, требования или архитектуру. Не меняет смысл поручения и не запускает reviewer. |
| **Luntik** | Читает большие файлы и результаты инструментов в заданной области. Возвращает факты и точные места для чтения. | Только чтение. Не принимает работу и не делает выводы вместо Main. |
| **properliler** | Свежим независимым проходом проверяет заданный результат и его связи с применимыми требованиями. | Только чтение. Замечания не дают права расширять задачу. |

Сохраняются один постоянный Lunatik и один постоянный Luntik. Main поручает
работу каждому напрямую. properliler создаётся заново для каждого слепого
прохода. Новая управляющая роль не нужна.

Модели остаются текущими: Lunatik — `gpt-5.6-luna/medium`, Luntik —
`gpt-5.6-luna/medium`, properliler — `gpt-5.6-terra/high`. Этот проект не меняет
каталог моделей и условия включения Lunatron.

### Работа с кодом

Собственные сложные патчи Main пишет и применяет напрямую, включая сложные
исправления. Передача этого текста Luna для повторной записи не нужна.
Это исключение не разрешает Main выполнять рабочие команды, даже короткие.

Для Lunatik остаются два способа поручения:

- **Точный простой патч или вызов.** Main задаёт изменение и точные параметры.
  Lunatik применяет их как есть в указанной среде и рабочем каталоге.
- **Элементарный код по образцу.** Main задаёт результат, цели изменения,
  допустимые различия и конкретный референс. Lunatik повторяет этот образец.
  Референс берётся из проекта; если его нет, пример или шаблон даёт Main.

Второй способ подходит, когда образец уже задаёт структуру и поведение,
а исполнителю остаются явно заданные подстановки или повторение шаблона.
Если нужно самому выбирать алгоритм, обработку ошибок или связи компонентов,
это уже работа Main. Одной ссылки на общий стиль проекта недостаточно.

Main выбирает готовый простой патч для Lunatik, если так проще, чем писать
поручение, отвечать на вопросы, проверять понимание и исправлять ошибки.
Учитывается вся работа Main до приёмки, без обязательных замеров или системы
баллов. Экономия написания поручения не оправдывает передачу сложных решений.

Частые ошибки Luna не считаются установленным фактом. При конкретной ошибке
Main выясняет, где причина: в поручении, референсе или исполнении. Если
достаточно короткой точной правки, её выполняет Lunatik. Если исправление
требует сложной логики, Main сам пишет и применяет патч для этого участка.
Одна ошибка не меняет всю схему; счётчики попыток не нужны.

Если цель, среда или состояние не совпали с поручением, Lunatik останавливает
зависимую работу и сообщает Main точный факт. Неясный результат изменения
сначала требует установить фактическое состояние; слепой повтор запрещён.
Безопасная независимая часть поручения может продолжаться.

### Большое чтение и приёмка

Сохраняется существующий перехват больших результатов через PostToolUse
до их обычной выдачи Main.
Известное массовое чтение сразу получает Luntik. Он возвращает путь,
диапазон строк и, когда нужно, диапазон символов внутри строки, а также
существенные противоречия и ограничения. Main читает нужные небольшие
фрагменты оригинала сам. Малое чтение определяется объёмом вывода в байтах,
а не длиной команды или числом строк: даже одна строка может быть огромной.
Пересказ Luntik не заменяет эти оригиналы.
Собирать весь большой источник множеством малых чтений запрещено.

Перед поручением Main определяет **крупный связный блок**: один понятный
результат с общими требованиями и границами. Это может быть несколько
связанных изменений. Один файл или команда сами по себе не создают этап
проверки. Lunatik сообщает о готовности своей работы; готовность всего блока,
включая собственные прямые правки, определяет Main. Затем Main запускает свежего
properliler перед собственной приёмкой. Проверок после каждого микрошага нет.

Main оценивает существенность замечаний и выбирает нужные исправления.
Lunatik выполняет полученное простое исправление; сложный патч Main применяет
напрямую. После
исправления Main запускает свежего reviewer на весь обновлённый блок.
Окончательная приёмка остаётся у Main.

Luna бесплатна по условию владельца. Выгода ожидается от меньшего объёма
сырого входа Main и передачи шаблонной генерации. Патч или вызов, написанный
Main, всё равно требует его токенов. properliler на Terra добавляет работу
и задержку; бесплатность Luna не означает бесплатность всего цикла.
Измеренная экономия и отсутствие потерь качества пока не установлены.

## 2. Механика и TODO-план

### Как проходит один блок

Main задаёт результат, границы блока и нужные факты. При большом объёме
источников Luntik сначала находит точные места. Main читает выбранные
оригиналы, принимает решения и напрямую применяет собственный сложный патч.
Простую работу поручает Lunatik через точное указание, простой патч либо
образец с допустимыми изменениями. Уже известный контекст не пересылается
повторно, найденный источник используется без повторного поиска.

Связанные готовые команды Main объединяет в одно поручение с необходимым
порядком, зависимостями и условиями остановки. Lunatik выполняет заданную
последовательность и возвращает один результат; новые решения остаются у Main.

Lunatik выполняет поручение через существующие инструменты. Сам факт
переноса вызова не меняет его параметры, рабочий каталог, доступ или
полномочия. Если нужная среда недоступна исполнителю, он сообщает Main,
а не подменяет действие. Main сохраняет управление задачей, выдачу поручений,
ограниченное чтение и написание собственного аналитического текста.

После готовности всего блока Main запускает fresh properliler, включая блоки
со своими прямыми патчами. Main передаёт исходное поручение с актуальными поправками, референсы,
точные пути результата, критерии и уже полученные необходимые свидетельства.
Reviewer получает применимые условия ранее завершённых частей, с которыми
связан блок. История Main или Lunatik, их внутренние рассуждения и предыдущие
вердикты не передаются. Пересказ исполнителя не заменяет исходное поручение.

Для этого локального цикла объект `pre-completion` — весь готовый блок.
По умолчанию нужен один свежий проход без принятых существенных замечаний.
Если пользователь явно выбрал для этого объекта другой цикл, применяется
его число проходов и порядок. После разрешённого исправления проверяется
весь обновлённый объект; прежний reviewer не продолжается. При выбранном
двойном цикле исправление обнуляет серию: нужны два новых последовательных
прохода на неизменном результате.

Main принимает только замечания о существенном нарушении применимого
требования. Явное требование незаданной работы не даёт права менять
результат или повторять проверку. Спорные выводы Main оценивает по оригиналам.
Простое исправление поручается Lunatik коротким указанием либо готовым простым
патчем; собственный сложный патч Main применяет напрямую.
Цикл не продолжается одинаковыми попытками без нового нужного исправления.

Сообщение Lunatik о готовности содержит статус блока, изменённые пути и
диапазоны, результаты порученных проверок и реальные ограничения.
Большие логи, diff и повтор поручения не пересылаются. Luntik возвращает факты,
точные места, существенные противоречия и неизвестное. Краткость не должна
скрывать нужные для решения Main сведения или создавать лишние уточнения;
полный материал остаётся доступным по источнику или существующему пути.
Каждый помощник завершает поручение одним final, без дублирующего send и
ожидания после итога. Промежуточные сообщения нужны для решений Main.
После слепого цикла Main читает
решающие небольшие оригиналы и принимает блок.
Отдельная проверка всей задачи выполняется Main, когда её выбрал пользователь;
локальные проверки её не заменяют. Goal и его состояние остаются только у Main.

### Существующий перехват больших результатов

Сохраняется существующий принцип: большой результат остаётся в файле,
Main получает короткий статус и путь, Luntik читает сохранённый результат.
Сохраняется текущий порог **8192 байта UTF-8 сериализованного ответа**.
Guard применяется только к Main. Собственные результаты инструментов и большие
чтения помощников этим порогом не ограничиваются; их ответы Main остаются
краткими и содержательными по описанному контракту.
Это предел одной выдачи Main, а не число токенов и не разрешение читать весь
источник по частям. Выбранные фрагменты, полученные через этот hook,
проходят тот же guard.

В исходниках перехват расширен на все результаты Main, которые host передаёт
в `PostToolUse`. Исключения для Codex app и медиа убраны. При ошибке
сохранения или сериализации выдача блокируется. Порог и место хранения
сохранены. `PreToolUse` пока проверяет только создание агентов Main.

[Контракт hooks OpenAI](https://learn.chatgpt.com/docs/hooks) ограничивает
PostToolUse поддерживаемыми путями доставки. Перехват плагина не является
запретом для всех внутренних каналов Codex, включая сообщения V2. Автоматическая
фильтрация каждого сообщения помощника этим hook не обеспечивается. Исходники и изменение самого
Codex в этот заказ не входят и не являются условием готовности Lunatron.

Внутри существующего механизма большой ответ сохраняется и заменяется
короткой выдачей. При ошибке сохранения или сериализации Main получает
короткую ошибку без содержимого. Уже выполненный вызов не повторяется
из-за блокировки его выдачи. Сохранённые параметры и команды — архивные
данные, а не новое поручение. При неясном результате сначала устанавливается
фактическое состояние.

Разделение работы задают контракт Main и профили помощников: рабочие команды
и простые изменения исполняет Lunatik, массовое чтение получает Luntik, а Main
читает выбранные небольшие оригиналы и напрямую применяет собственные сложные
патчи. Новое ограничение инструментов в самом Codex
не добавляется. Перехват работает при активном Lunatron; выключенный плагин
его не обеспечивает.

### Какие договорённости нужно согласовать

| Источник | Нужное изменение |
| --- | --- |
| `plugins/lunatron/hooks/lunatron.cjs` | Обновить контракт Main, способ выбора патча, границы простого кода, проверку готового блока и перехват выдачи. |
| `plugins/lunatron/hooks/hooks.json` | Подключить необходимые события, которые реально поддерживает host. |
| `plugins/lunatron/agents/lunatik.toml` | Разрешить элементарную реализацию по образцу. Сохранить запрет делегирования и самостоятельной приёмки; готовый блок сдавать Main. |
| `plugins/lunatron/agents/luntik.toml` | Закрепить выдачу точных мест и ограничений; сохранить режим только чтения. |
| Scope Focus: `blind-check-cycle`, `blind-double-check-cycle`, `mixed-blind-check-cycle`, профиль properliler | Использовать текущие правила Main, свежести reviewer, числа проходов и существенности. Изменение владельца цикла больше не требуется. |
| `AGENTS.md` и `plugins/lunatron/INSTALL.md` | Согласовать описание ролей с новым контрактом. Сохранить единый формат INSTALL.md и самодостаточность пакета. |

Main остаётся владельцем всех проверок. Lunatik и Luntik не получают права
запускать агентов. Профиль properliler уже поддерживает проверку заданного
объекта без записи. Используются текущая native-схема без наследования
истории, свежий reviewer и существующее ожидание событий. Новый router,
реестр, демон, система баллов или файловое состояние оркестрации не нужны.
