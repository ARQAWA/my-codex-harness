# Рабочая база

Заморожены до прямой разморозки владельцем только приватный форк Codex CLI и
патч VS Code Extension. Их исходники и история Git сохраняются как архивный
baseline; развитие, Check/Update, сборка, release, push и установка не
выполняются, общий заказ разморозку не заменяет. Codex-части Scope Focus и
Lunatron и Codex-промпт разморожены владельцем 2026-10-06: их развитие, release,
push и установка выполняются по заказу. Штатный Codex App/CLI как инструмент
работы не заморожен. Runtime, данные, настройки и секреты этим статусом не
изменяются.

Этот репозиторий — рабочая база Scope Focus, Lunatron
и отдельного системного промпта.

Источники правды после импорта:

- `plugins/scope-focus`
- `plugins/lunatron`
- `new-model-instructions.md`
- `INSTALL_FOR_AGENTS.md`
- `install-instructions/`

Runtime-копии `~/.codex/plugins/cache` и прежние `~/plugins` отдельны.
Текущий импорт их не меняет. Дальнейшая разработка идёт здесь, установка
выполняется отдельно.

Все plugin manifest используют `0.0.0+codex.YYYYMMDDHHMMSS`; timestamp — UTC.
Для штатного bump используется `node tools/update-plugin-cachebuster.mjs <plugin> [...]`
из этого репозитория, без внешнего plugin-creator. Новый plugin
сразу получает этот формат. Для source release каждого изменённого plugin
выполняется один bump перед source commit. Обычное редактирование без release
и install/update без source changes версию не меняют. Timestamp вручную не
придумывать и повторный bump не делать.

## Локальная проверка исходников

Единая детерминированная проверка репозитория запускается командой
`node tests/run.mjs`. Она не заменяет install-time проверки на целевой ОС из
`install-instructions/*.md` и не меняет активный Codex home.

## A/B-оценка Cursor против Codex

`tools/ab-eval.mjs` служит только для сравнения A/B-прогонов одной задачи
в Cursor и Codex и в поставку не входит. Скрипт читает rollout Codex и базу
Cursor только на чтение, считает время и токены генерации каждой стороны
и пересчитывает обе на меньшую из двух скоростей генерации. Токены Cursor
оцениваются по видимому тексту с отношением символов к токенам из rollout
Codex. Запуск: `node tools/ab-eval.mjs --codex <session-id> --cursor <composer-id>`.

## Политика

Scope Focus задаёт always-on точный scope, широкое чтение и минимальный
результат. Quality adjectives не расширяют scope.

Goal ограничен формулированием и native goal. Root Main автоматически ставит его
для длинной многоэтапной задачи только при явном постоянном поручении либо
применимой вышестоящей инструкции и допускающих это native rules. Прямой $goal
выбирает режим, «без Goal» исключает автоматический выбор.
Task Notebook ведётся автоматически для задачи из нескольких зависимых этапов
работы, например исследование, план и пошаговая реализация или автоматизация;
задаче с одним ответом, документом или короткой правкой он не нужен, сколько бы
она ни читала, ни ждала и ни занимала контекст. Прямой выбор требует его
ведения, явный запрет имеет приоритет. Blind review запускается только явным
выбором пользователя, шагами ToSpec и обязательным gate финализации ниже.
Goal Compiler и raw bundles — прежний дизайн;
в текущем составе goal skill этого нет.

### Обязательный gate финализации

Перед сдачей задачи с изменениями в этом репозитории, commit, push и завершением
release Main обеспечивает применение
[finalize-work](.agents/skills/finalize-work/SKILL.md): если skill делегирован,
его читает и исполняет назначенный исполнитель; иначе Main читает и исполняет его.
Это постоянное прямое поручение пользователя на слепой light review согласованности
кода и всей документации сдаваемого результата, отсутствия устаревших действующих
сведений, мусора и конфликтов. Gate распространяется и на документационные правки.
Без CLEAN от свежего Spotty завершение, commit и push запрещены. Существенные
замечания исправляются до CLEAN по процедуре skill. Не повторяй уже пройденный
gate для неизменённого результата и оснований. Сам gate не разрешает публикацию.

### Контракт разрабатываемого Lunatron

Этот подраздел описывает runtime-контракт Lunatron и сам его не активирует.
При `LUNATRON_STATE=ACTIVE` hook требует прочитать bundled skill
`lunatron-delegation`; поручение на делегирование блоков даёт только этот skill
и только для активной корневой задачи; отдельное поручение Gold Standard на
быстрые read-only explorer для широкого поиска действует без Lunatron, если
пользователь не запретил субагентов. Reviewer запускается по прямому запросу
пользователя, шагам ToSpec или постоянному поручению на gate выше.

Цель — более быстрый результат: независимые блоки идут параллельно, шумный
вывод остаётся у исполнителя, передачи короткие. Main делегирует только большой
блок, независимый от своего следующего шага и выполнимый параллельно; короткую
и последовательную работу, включая небольшие скрипты, CLI, запуски и тесты,
делает сам. Main сохраняет scope, решения, приёмку, native Goal и ответ. Scope Focus и
Lunatron не ограничивают Main ролями Lunatron и не запрещают других разрешённых
агентов; Main может целиком поручить выбранный skill, кроме `goal`, подходящему
субагенту в границах его блока.

Роли закреплены профилями: `lunatik` (`gpt-6-luna/medium`) — свежий полный форк
для исполнения; `lunatron_luna_high` (`gpt-6-luna/high`)
— сложный блок; `lunatron_sol_low`, `lunatron_sol_medium`, `lunatron_sol_high`
(`gpt-6.1-sol` с соответствующим effort) — блок, которому нужен более сильный
анализ. Main на Luna использует только Luna. Sol реализует свой блок сам или
форкает Luna для большой независимой части; обязательной цепочки Main→Sol→Luna,
запрета передавать код и Sol→Sol цепочек нет.

Форк наследует историю, поэтому бриф — несколько строк: результат, цели, cwd и
решения, которые нужно сохранить; snippet или точная правка допустимы, если они
короче описания. Final краткий и без пересказа хода работы: статус, результат,
изменённые пути, ключевые факты с file:line, результаты проверок, ошибки,
неизвестное. Родитель использует его без перепроверки. Завершённых помощников
закрывают в одном batch со следующим вызовом, если есть инструмент закрытия;
событий ждут только при блокировке. При недоступной роли или форке блок
выполняется напрямую. `capture.cjs` и `context.cjs` нужны только для очень
больших выводов. `LNT0` останавливает помощников текущей задачи, устанавливает
состояние прерванных изменений и закрывает их, когда возможно; отсутствие
закрытия не блокирует выключение. Установочный минимум
`agents.max_concurrent_threads_per_session` — 44 с сохранением более высокого
значения.
Подробный runtime-контракт находится в
[`plugins/lunatron/hooks/lunatron.cjs`](plugins/lunatron/hooks/lunatron.cjs)
и профилях `plugins/lunatron/agents`; этот файл не заменяет их.
### Правила работы с исходниками

Доступность и версию моделей определяет штатный Codex. Репозиторий закрепляет
модель и effort узких ролей в их профилях, но не поставляет кастомный каталог
моделей и не закрепляет их внутренние версии.

Общая execution policy работает без Goal. Единственное runtime-состояние
управления Lunatron — заказанный файл режима `LNT` текущей задачи. Не добавлять
другой router, state, toggle или enforcement вместо prompt.

Обычная проверка — чтение и логика. После изменений кода или конфигурации один
раз запускать существующие проверки, покрывающие изменение (`node tests/run.mjs`),
по возможности в фоне; повторять только после исправления выявленного ими сбоя.
Сбои от изменения, включая прежние утверждения о намеренно изменённом поведении,
исправлять; посторонние сбои сообщать без починки. Новые тесты, фикстуры, замеры,
опыты и проверки сверх покрывающих изменение — только по прямому запросу или
конкретно принятой процедуре.

Для проверочных запусков Lunatron использовать самую дешёвую подходящую
модель: тестовый Main — `gpt-6-sol` с `model_reasoning_effort = "low"`.
Не запускать для этих проверок Astra и не повышать модель или reasoning
самостоятельно. Lunatik использует профиль проверяемой версии.

Сохранять пользовательские изменения. В migration без запроса не менять
location, format или value секретов.

Tritron и Lunatron не смешивать в runtime. Tritron не входит в этот snapshot.
Lunatron по умолчанию выключен для корневой задачи независимо от модели;
автоматического выбора по модели нет.
Слитные `LNT1` и `LNT0` в любом регистре включают и выключают режим текущей задачи.
Плагин и все hooks включаются при установке и обновлении.
При `LNT0` Main останавливает работающих помощников текущей задачи, устанавливает
состояние прерванных изменений и закрывает помощников доступным штатным способом.
Отсутствие закрытия не блокирует выключение. Синтаксис команд
и подключение описаны в `install-instructions/lunatron.md`.

Новая версия и установка не следуют из обычного редактирования. Временные файлы
задачи удаляются по точному пути в последней использующей их команде, Notebook
завершённой задачи переносится в корзину в batch с последним рабочим вызовом;
пауза, ожидание, блокер или указание сохранить его оставляют. Cleanup skills и
очистка всей сессии — только по прямому запросу.
Порядок release описан в `.agents/skills/release/SKILL.md`.

`INSTALL_FOR_AGENTS.md` — единая точка входа для установки и обновления.
Источники действий установки — этот входной документ, инструкция выбранного
компонента из `install-instructions/` той же ревизии и её явно указанные
зависимости. Репозиторный `AGENTS.md` описывает разработку и находится вне
процедуры установки.
Документы других плагинов разрешено читать и выполнять только в части явно
объявленных обязательных зависимостей выбранного plugin. Уже подготовленные
совместимые зависимости переиспользуются; остальные функции и полная установка
другого plugin автоматически не запускаются:
`scope-focus.md` или `lunatron.md`. Системный промпт
устанавливается отдельно по `install-instructions/system-prompt.md`, когда он
входит в запрос. Все инструкции сохраняют общий порядок разделов:
состав, требования, первая установка,
проверка после установки, обновление.

Инструкции и ссылки на них не входят в plugin package, manifest, runtime skills,
hooks или обычные runtime-инструкции. Системный промпт — отдельный компонент
поставки, его исходник — `new-model-instructions.md`. Прямой `codex plugin add`
не выполняет repo-level инструкции автоматически.
На этом macOS-хосте Codex CLI находится внутри Codex App: `/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex`; если команда `codex` недоступна в `PATH`, запускай этот исполняемый файл по абсолютному пути.

JSON сохранять в UTF-8 с читаемыми символами, без замены кириллицы на
Unicode-последовательности вида \uXXXX. После инструментов смены версии
сохранять этот формат, не меняя значения полей при пересериализации.

`install-instructions/*.md` и справочные тексты должны быть короткими и
содержательными.
Описывай конкретный состав, отдельно подключаемые части и готовность пакета.
В инструкциях установки плагинов нужны ясные шаги штатной установки и
обновления через Codex CLI, включая выбор marketplace и `codex plugin add`.
Для отдельного системного промпта указывай ключ `model_instructions_file`
в `config.toml`, реальный путь целевой машины и отличие от содержимого плагинов.
Достаточные команды и примеры настроек допустимы здесь; они не переходят в
runtime skills.
Доверие к hooks устанавливается через штатный Codex app-server по текущим
определениям; обход trust запрещён. Проверки из выбранного документа
`install-instructions/*.md` выполняет
устанавливающий агент в конце установки на целевой ОС. В Windows — только
через Git Bash; результат другой ОС не доказывает работу Windows.
Редактирование исходников и документации само по себе не запускает эти
проверки. При update сохраняй данные, секреты и чужие настройки; повторяй
только требуемые проверки затронутых частей. Явный запрет пользователя на
проверочные запуски имеет приоритет. Не включай посторонние функции хоста
из-за сходства их имени с именем плагина.

Дизайн-файл каждого плагина описывает только этот плагин и его необходимые внешние контракты. Не помещать план, требования реализации или правки одного плагина в дизайн другого. Общие правила репозитория хранятся в AGENTS.md. При совместном апгрейде отдельно сверять взаимодействие плагинов в рамках заказанного объёма и выбранной процедуры; раздельная приёмка каждого плагина не заменяет эту сверку.

Дизайн-файл описывает действующую концепцию плагина: назначение, проблемы, контекст, актуальные предложения, принятые решения, согласования пользователя и причины устройства. Различать предложение, согласованное решение и фактически выполненное изменение; не приписывать согласования или результаты. Прежние версии доступны в истории Git/GitHub. Не помещать в дизайн рабочие TODO, очереди выполнения и чек-листы релиза. Текущий план и статус работы ведутся в достаточном первичном источнике; при полезном отдельном состоянии применяется Task Notebook без копирования технического плана. Текущие инструкции установки находятся в соответствующем `install-instructions/<plugin>.md`.

При удалении компонента, кода или отказе от решения удаляй относящиеся к нему
действующие исходники и документацию. Не создавай архивные копии, заметки,
записи об удалении или отказе ради сохранения прошлого: для этого используется
история коммитов Git/GitHub. Правило действует в этом репозитории,
`codex-harness` и `codex-vscode-harness`. Оно не разрешает удалять пользовательские
данные, включая оригиналы разговоров LCM, и не отменяет документацию действующих
решений и выполненной работы.

После repo-level setup runtime-пакет каждого plugin самодостаточен и не зависит
от документации репозитория. Установка и обновление из репозитория используют
документ выбранной ревизии. Этот файл задаёт правила работы над исходниками.

Не добавлять setup skills. Не ссылаться на рабочий репозиторий в файлах
плагинов.

Общие инструкции модели описывают поведение и принципы работы без привязки к
конкретным функциям, командам и переменным окружения. Системный промпт Codex
полностью самодостаточен и независим от плагинов и других механик harness.
Он не содержит связей с конкретными плагинами, их workflows, состоянием или
файлами и работает без их установки.
Правила Goal, Notebook, cleanup и маршрутизации принадлежат соответствующим
плагинам; изменения этих правил не переносятся в базовые промпты. Общие
правила использования доступных инструментов не требуют их наличия.
Конкретная механика инструментов Codex — лимиты вывода, code mode, CLI чтения —
находится в skill Scope Focus `codex-tools` и подаётся hook вместе с Gold Standard.

Всё собственное tooling проекта, включая hooks, реализуется на Node.js и
должно работать на macOS, Linux и Windows.
В Windows работать строго через Git Bash. PowerShell запрещён.

MCP запрещены в этом репозитории, в том числе внутри плагинов и субагентов.
