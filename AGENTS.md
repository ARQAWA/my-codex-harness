# Рабочая база

Этот репозиторий — рабочая база Scope Focus, Lunatron
и отдельного системного промпта.

Источники правды после импорта:

- `plugins/scope-focus`
- `plugins/lunatron`
- `new-model-instructions.md`
- `INSTALL_FOR_AGENTS.md`
- `install-instructions/`

Runtime-копии `~/.codex/plugins/cache` и прежние `~/plugins` отдельны.
Текущий импорт их не меняет. Дальнейшая разработка идёт здесь, установка
выполняется отдельно.

Все plugin manifest используют `0.0.0+codex.YYYYMMDDHHMMSS`; timestamp — UTC.
Для штатного bump используется `node tools/update-plugin-cachebuster.mjs <plugin> [...]`
из этого репозитория, без внешнего plugin-creator. Новый plugin
сразу получает этот формат. Для source release каждого изменённого plugin
выполняется один bump перед source commit. Обычное редактирование без release
и install/update без source changes версию не меняют. Timestamp вручную не
придумывать и повторный bump не делать.

## Локальная проверка исходников

Единая детерминированная проверка репозитория запускается командой
`node tests/run.mjs`. Она не заменяет install-time проверки на целевой ОС из
`install-instructions/*.md` и не меняет активный Codex home.

## Политика

Scope Focus задаёт always-on точный scope, глубокое понимание и минимальное
действие. Quality adjectives не расширяют scope.

Goal нужен только для формулирования и native goal. Task Notebook и дополнительные
blind review опциональны при явном выборе; обязательный gate финализации описан ниже.
Goal Compiler и raw bundles — прежний дизайн;
в текущем составе goal skill этого нет.

### Обязательный gate финализации

Перед сдачей задачи с изменениями в этом репозитории, commit, push и завершением
release Main обеспечивает применение
[finalize-work](.agents/skills/finalize-work/SKILL.md): если skill делегирован,
его читает и исполняет назначенный исполнитель; иначе Main читает и исполняет его.
Это постоянное прямое поручение пользователя на слепой light review согласованности
кода и всей документации сдаваемого результата, отсутствия устаревших действующих
сведений, мусора и конфликтов. Gate распространяется и на документационные правки.
Без CLEAN от свежего Spotty завершение, commit и push запрещены. Существенные
замечания исправляются до CLEAN по процедуре skill. Не повторяй уже пройденный
gate для неизменённого результата и оснований. Сам gate не разрешает публикацию.

### Контракт разрабатываемого Lunatron

Этот подраздел описывает runtime-контракт Lunatron. Сам по себе этот текст
не активирует Lunatron.
При `LUNATRON_STATE=ACTIVE` hook Lunatron требует загрузить bundled skill
`lunatron-delegation`; источник поручения на делегирование — только этот skill.
При неактивном Lunatron skill не поручает делегирование; других субагентов
запускают по прямому запросу.
Reviewer запускается только по
прямому запросу пользователя, включая постоянное поручение на gate выше.
Описанные ниже роли, обязательная делегация и packaged tooling относятся
только к runtime-контракту разрабатываемого плагина.

Главная цель Lunatron — изоляция шумной работы от контекста Main; экономия
ресурсов вторична. Scope Focus и Lunatron не ограничивают Main двумя ролями
Luna и не запрещают других разрешённых агентов. Main выбирает skills и может
использовать других workers с учётом модельных ограничений ниже. Main может
целиком поручить любой выбранный skill, кроме `goal`, подходящему
субагенту в границах его блока. Субагент сам читает фактический `SKILL.md` и
исполняет процедуру. Постановка и управление native Goal остаются только в
корневом чате Main. Полномочия, ограничения роли и самого skill сохраняются; выбор
skill не расширяет заказанный объём. Main управляет задачей и решениями.
Все агенты доверяют готовым результатам друг друга; передачу работы не
сопровождают повторной проверкой. Review выполняет
только reviewer, которому явно поручили запрошенное review. Исполнитель
передаёт достаточный для продолжения результат: Main не получает автоматически
внутреннюю историю работы форка. Достаточность важнее краткости.
Свежий полный форк Lunatik на `gpt-6-luna/medium` выполняет простую
реализацию и механику; постоянный Luntik на `gpt-6-luna/medium` отвечает на
простой смысловой вопрос к выбранным большим данным. Main Luna использует только
Luna, включая `lunatron_luna_xhigh` (`gpt-6-luna/xhigh`) для сложного блока.
Любой Main вне Luna может выбрать Luna XHigh или владельца сложного Sol-блока:
`lunatron_sol_low` (`gpt-6.1-sol/low`) — регулярная сложная аналитика, когда
Luna Medium/XHigh недостаточны; `lunatron_sol_medium` (`gpt-6.1-sol/medium`) —
очень сложная; `lunatron_sol_xhigh` (Sol Extra High, `gpt-6.1-sol/xhigh`) —
исключительно тяжёлая. Достаточный уровень выбирается сразу, без лестницы проб;
Sol `max` не наследуется. Reviewer определяется своим review-skill независимо
от пула workers. Недоступность обязательной роли или полного форка останавливает
зависимый блок без подмены.
Sol сам анализирует свой блок, принимает решения в его границах, формулирует и
сохраняет аналитику, документацию, инструкции и промпты, включая embedded prose.
Для обычной кодогенерации любой сложности и разрешённой механики/запусков он
назначает собственных Luna полным форком своего текущего контекста: Lunatik для
простой реализации, Luna XHigh для сложной. Форк разговора не является Git worktree.
Sol даёт достаточный описательный план с результатом, scope, cwd, ownership,
поведением, потоком данных, интерфейсами, алгоритмом словами, error policy,
точными существующими references/API/values, порядком, разрешёнными действиями и
условиями возврата. Новые готовые code bodies, patches/diffs/snippets и копируемый
implementation pseudocode не передаются; существующий и пользовательский код —
данные. Luna сама генерирует реализацию. Только действительно неотделимую часть
Sol может написать сам, указав конкретную причину; сложность, удобство или
недоступный slot/профиль не являются основанием. Авторство не разрешает новые runs.
Право Sol ограничено собственными Luna execution blocks: без Sol→Sol цепочек,
передачи всего заказа planner и root orchestration. Child INACTIVE снимает root
обязанности, сохраняя это право профиля; Luna не получает произвольного права
создавать workers. Luna сообщает final своему непосредственному Main либо Sol;
Sol завершает весь блок и сообщает Main. Родитель использует достаточный итог
как готовый вход, без reread originals, повторных исследований/checks или review.
Приёмка Main не является новой инспекцией кода. Чтение для новой работы либо
конкретного пробела/проблемы и явно заказанный reviewer сохраняют свои границы.
Нормальное общение — одно назначение и один final, без дублирующего send. При
существенном пробеле исполнитель возвращает DECISION_REQUIRED непосредственному
владельцу; тот решает словами в своих полномочиях и при необходимости назначает
свежий блок. Root-решения остаются Main.
Готовые независимые необходимые Sol/Luna блоки запускаются параллельно с
ownership общих файлов и порядком зависимостей. Все потомки — Sol, Luna, Luntik и
reviewers — делят фактическую native ёмкость. Заказанный предел
`agents.max_concurrent_threads_per_session` — 44 без Main; установочный минимум
44 сохраняет более высокие user settings. Отдельного cap15 или квот нет; сохраняй
место требуемым Luna, не заполняй ёмкость только Sol-координаторами. Active-turn и
open-thread budget различны; config не доказывает live capacity. Нехватка
обязательного slot — конкретный blocker, без нового scheduler/state/max_depth.
При зависимости от ребёнка и отсутствии независимой необходимой работы агент
немедленно ждёт native event-driven wait с длинным допустимым timeout (до
1200000 ms в пределах инструмента), без polling, повторной работы/анализа и
неизменных комментариев. Таймаут не доказывает сбой. Это не обещание бесплатного
workflow или измеренной скорости.
Каждый one-shot заканчивает final и ход. Непосредственный родитель закрывает его
доступной native операцией с успешным acknowledgment, включая error results:
Sol — своих Luna, Main — своих Sol и прямых Luna. Одноразовые id не переиспользуются.
Final/interrupt не доказывают closure или освобождение open-thread slot; при
недоступном close честно сообщается ограничение и используется реальная ёмкость,
без собственного клиента, удаления истории или архивации чата. LNT0 останавливает
всё дерево текущей Main-задачи, устанавливает interrupted state и закрывает
доступным способом; чужие задачи исключены, отсутствие close не мешает выключению.
Подробный runtime-контракт находится в
[`plugins/lunatron/hooks/lunatron.cjs`](plugins/lunatron/hooks/lunatron.cjs)
и профилях `plugins/lunatron/agents`; этот файл не заменяет их.

### Правила работы с исходниками

Доступность и версию моделей определяет штатный Codex. Репозиторий закрепляет
модель и effort узких ролей в их профилях, но не поставляет кастомный каталог
моделей и не закрепляет их внутренние версии.

Общая execution policy работает без Goal. Единственное runtime-состояние
управления Lunatron — заказанный файл режима `LNT` текущей задачи. Не добавлять
другой router, state, toggle или enforcement вместо prompt.

Обычная проверка — чтение и логика. Эмпирические проверки выполнять только по
прямому запросу или конкретно принятой процедуре.

Для проверочных запусков Lunatron использовать самую дешёвую подходящую
модель: тестовый Main — `gpt-6-sol` с `model_reasoning_effort = "low"`.
Не запускать для этих проверок Astra и не повышать модель или reasoning
самостоятельно. Luntik и Lunatik используют профили проверяемой версии.

Сохранять пользовательские изменения. В migration без запроса не менять
location, format или value секретов.

Tritron и Lunatron не смешивать в runtime. Tritron не входит в этот snapshot.
Lunatron по умолчанию выключен для корневой задачи независимо от модели;
автоматического выбора по модели нет.
Слитные `LNT1` и `LNT0` в любом регистре включают и выключают режим текущей задачи.
Плагин и все hooks включаются при установке и обновлении.
При `LNT0` Main останавливает работающих помощников текущей задачи, устанавливает
состояние прерванных изменений и закрывает помощников доступным штатным способом.
Отсутствие закрытия не блокирует выключение. Синтаксис команд
и подключение описаны в `install-instructions/lunatron.md`.

Новая версия, установка и cleanup не следуют из обычного редактирования.
Порядок release описан в `.agents/skills/release/SKILL.md`.

`INSTALL_FOR_AGENTS.md` — единая точка входа для установки и обновления.
Источники действий установки — этот входной документ, инструкция выбранного
компонента из `install-instructions/` той же ревизии и её явно указанные
зависимости. Репозиторный `AGENTS.md` описывает разработку и находится вне
процедуры установки.
Документы других плагинов разрешено читать и выполнять только в части явно
объявленных обязательных зависимостей выбранного plugin. Уже подготовленные
совместимые зависимости переиспользуются; остальные функции и полная установка
другого plugin автоматически не запускаются:
`scope-focus.md` или `lunatron.md`. Системный промпт
устанавливается отдельно по `install-instructions/system-prompt.md`, когда он
входит в запрос. Все инструкции сохраняют общий порядок разделов:
состав, требования, первая установка,
проверка после установки, обновление.

Инструкции и ссылки на них не входят в plugin package, manifest, runtime skills,
hooks или обычные runtime-инструкции. Системный промпт — отдельный компонент
поставки, его исходник — `new-model-instructions.md`. Прямой `codex plugin add`
не выполняет repo-level инструкции автоматически.
На этом macOS-хосте Codex CLI находится внутри Codex App: `/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex`; если команда `codex` недоступна в `PATH`, запускай этот исполняемый файл по абсолютному пути.

JSON сохранять в UTF-8 с читаемыми символами, без замены кириллицы на
Unicode-последовательности вида \uXXXX. После инструментов смены версии
сохранять этот формат, не меняя значения полей при пересериализации.

`install-instructions/*.md` и справочные тексты должны быть короткими и
содержательными.
Описывай конкретный состав, отдельно подключаемые части и готовность пакета.
В инструкциях установки плагинов нужны ясные шаги штатной установки и
обновления через Codex CLI, включая выбор marketplace и `codex plugin add`.
Для отдельного системного промпта указывай ключ `model_instructions_file`
в `config.toml`, реальный путь целевой машины и отличие от содержимого плагинов.
Достаточные команды и примеры настроек допустимы здесь; они не переходят в
runtime skills.
Доверие к hooks устанавливается через штатный Codex app-server по текущим
определениям; обход trust запрещён. Проверки из выбранного документа
`install-instructions/*.md` выполняет
устанавливающий агент в конце установки на целевой ОС. В Windows — только
через Git Bash; результат другой ОС не доказывает работу Windows.
Редактирование исходников и документации само по себе не запускает эти
проверки. При update сохраняй данные, секреты и чужие настройки; повторяй
только требуемые проверки затронутых частей. Явный запрет пользователя на
проверочные запуски имеет приоритет. Не включай посторонние функции хоста
из-за сходства их имени с именем плагина.

Дизайн-файл каждого плагина описывает только этот плагин и его необходимые внешние контракты. Не помещать план, требования реализации или правки одного плагина в дизайн другого. Общие правила репозитория хранятся в AGENTS.md. При совместном апгрейде отдельно сверять взаимодействие плагинов в рамках заказанного объёма и выбранной процедуры; раздельная приёмка каждого плагина не заменяет эту сверку.

Дизайн-файл описывает действующую концепцию плагина: назначение, проблемы, контекст, актуальные предложения, принятые решения, согласования пользователя и причины устройства. Различать предложение, согласованное решение и фактически выполненное изменение; не приписывать согласования или результаты. Прежние версии доступны в истории Git/GitHub. Не помещать в дизайн рабочие TODO, очереди выполнения и чек-листы релиза. Текущий план и статус работы ведутся в выбранном Task Notebook; текущие инструкции установки находятся в соответствующем `install-instructions/<plugin>.md`.

При удалении компонента, кода или отказе от решения удаляй относящиеся к нему
действующие исходники и документацию. Не создавай архивные копии, заметки,
записи об удалении или отказе ради сохранения прошлого: для этого используется
история коммитов Git/GitHub. Правило действует в этом репозитории,
`codex-harness` и `codex-vscode-harness`. Оно не разрешает удалять пользовательские
данные, включая оригиналы разговоров LCM, и не отменяет документацию действующих
решений и выполненной работы.

После repo-level setup runtime-пакет каждого plugin самодостаточен и не зависит
от документации репозитория. Установка и обновление из репозитория используют
документ выбранной ревизии. Этот файл задаёт правила работы над исходниками.

Не добавлять setup skills. Не ссылаться на рабочий репозиторий в файлах
плагинов.

Общие инструкции модели описывают поведение и принципы работы без привязки к
конкретным функциям, командам и переменным окружения.

Всё собственное tooling проекта, включая hooks, реализуется на Node.js и
должно работать на macOS, Linux и Windows.
В Windows работать строго через Git Bash. PowerShell запрещён.

## MCP и простое tooling

MCP запрещены в этом репозитории, в том числе внутри плагинов и субагентов.
Не добавлять собственные MCP-серверы, клиенты, обёртки или обязательные
MCP-настройки.

Tooling строить самым простым достаточным способом: инструкции, промпты,
skills, субагенты, плагины и обычные CLI-инструменты на Node.js.
Не усложнять эту механику без прямого запроса пользователя.

## Собственный Codex CLI

### Заказанный состав поставки

Поставка CLI — один полный архив для macOS Apple Silicon ARM64 и один для
Windows 11 Microsoft VDI x86_64. Голосовой патч Extension поставляется готовым
target VSIX из `codex-vscode-harness`; нужные target определяет текущий заказ.
Пользователю важен самый простой рабочий путь установки/обновления агентом,
а не физически один executable. Внутренние companions/runtime/лицензии входят
в соответствующий пакет и не являются отдельными продуктами.

Использовать existing package builder и private Release assets с checksum;
не делать самораспаковывающийся launcher или объединение программ ради числа
файлов. Не добавлять платформы, виды приложений или лишние сборки автоматически.
Не пересобирать неизменённый VSIX при update только CLI. Tracked инструкции
должны задавать target, asset/version/hash, распаковку/установку и обновление
с сохранением настроек, секретов и данных. Наличие инструкции не разрешает
установить пакет без соответствующего поручения.

Единый production-вход CLI — `node scripts/build_harness.mjs --source <S>
--target all` из `../codex-harness`, по его `UPDATING.md`. Не составлять
альтернативные ручные рецепты сборки из чата. Скрипт использует pinned inputs
и existing primitives; установка и публикация остаются отдельными действиями.

Повторная локальная сборка использует сохранённые Cargo/Bazel outputs и pinned
inputs по [UPDATING.md](../codex-harness/UPDATING.md), раздел «Быстрые повторные
сборки». Не начинать с пустого target/cache и не делать clean при обычном update
или cleanup задачи. Собирать только компоненты согласованной поставки; готовые
неизменённые inputs не пересобирать ради новой упаковки или документации.
Скорость не оправдывает устаревшие бинарники, неверный source SHA, отключение
