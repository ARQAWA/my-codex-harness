# Рабочая база

Этот репозиторий — рабочая база Scope Focus, отдельного системного промпта и
расширения ARQAWA CCLI для VS Code. Пользовательский harness синхронизируется
с [my-pi](https://github.com/ARQAWA/my-pi); механика инструментов своя для
Codex.

Источники правды:

- `plugins/scope-focus`
- `new-model-instructions.md`
- `WORKFLOW-MANIFEST.md`: личный манифест владельца, см. «Политика»
- `INSTALL_FOR_AGENTS.md`
- `install-instructions/`
- `SCOPE-FOCUS-DESIGN.md`
- `codex-cli-vscode/` (расширение ARQAWA CCLI, отдельно от плагина)

Runtime-копия `~/.codex/plugins/cache` отдельна.
Разработка идёт здесь, установка выполняется отдельно.

Заморожены до прямой разморозки владельцем приватный форк Codex CLI
`ARQAWA/codex-harness` и патч VS Code Extension `ARQAWA/codex-vscode-harness`:
их не читать, не искать и не менять. Общий заказ их не размораживает.

Plugin manifest использует `0.0.0+codex.YYYYMMDDHHMMSS`; timestamp — UTC.
Для штатного bump используется `node tools/update-plugin-cachebuster.mjs <plugin> [...]`
из этого репозитория, без внешнего plugin-creator. Новый plugin
сразу получает этот формат. Для release каждого изменённого plugin
выполняется один bump перед слиянием в `master`. Обычное редактирование без
release и install/update без source changes версию не меняют. Timestamp вручную
не придумывать и повторный bump не делать.

## Локальная проверка исходников

Единая детерминированная проверка репозитория запускается командой
`node tests/run.mjs`. Она не заменяет install-time проверки на целевой ОС из
`install-instructions/*.md` и не меняет активный Codex home.

## Политика

[`WORKFLOW-MANIFEST.md`](WORKFLOW-MANIFEST.md) — личный манифест владельца,
общий с my-pi: принципы работы, а не требования и не условие допуска изменений.
Он меняется только прямой правкой владельца, его прямой просьбой или явным
согласием на предложенную правку.

Scope Focus переносит в Codex пользовательскую часть my-pi: системный промпт —
`extensions/RQW-prompt/SYSTEM.md` плюс блок Communication из
`extensions/RQW-dyslexia`, review — `extensions/RQW-review`, приёмы чтения и
поиска — `extensions/RQW-tools`. Механика своя для Codex. Quality adjectives
не расширяют scope.

Координатор my-pi, его `coordinator.lock`, `PROCESS.md`, `AGENTS.md`,
`DECISIONS.md`, матрица моделей исполнителей, профили и расширения в `.pi/` —
локальная разработка репозитория my-pi. Они не входят в пользовательский
harness и сюда не переносятся. Сюда переносится только то, что получает
пользователь my-pi: промпт, инструменты, субагенты и review.

Hook `SessionStart` подаёт root Main `codex-tools` с путями CLI чтения и todo
CLI, `todo` и строку окружения; при resume и compact ещё открытый
todo-список. `SubagentStart` подаёт субагенту только `codex-tools`, остальное
он берёт из профиля и брифа. Root Main ведёт собственный todo-список через CLI
`tools/todo.cjs`: CLI пишет список сессии в `<CODEX_HOME>/scope-focus-todo`,
hook `UserPromptSubmit` подаёт его или напоминание создать; hook `Stop` один раз
за ход возвращает модель к пунктам `pending` и `in_progress`; всего hooks четыре. Вызов todo CLI Main делает
в том же `exec`, что и работу. Root Main ведёт todo-список для задачи, которая
меняет файлы или идёт в несколько этапов. Review идёт только по просьбе
пользователя: `$blindreview` и `$highreview` запускают уровни blind и high по
skill `reviewer`; без указания уровня идёт blind. Сам Main и автоматические процессы
ревьюеров не запускают.
`$define-goal` записывает в цель дословные цитаты пользователя и раздел
Completion с проверками критериев. Gate финализации при release Main проходит
сам, без ревьюеров. Находки и отказы review опираются на
дословные цитаты согласия и объекта. Вопросы пользователю идут в чате в
формате вопросов системного промпта, без карточек.

Main не придумывает обязательные команды, форматы метаданных, лимиты и обещания
не трогать файлы.

Main пишет код, конфигурацию, документацию и промпты, запускает программы и
выбирает способ выполнения задачи. Плагин не задаёт правил запуска обычных
субагентов: действует штатная подсказка Codex, разрешающая их только по явной
просьбе пользователя или инструкциям AGENTS.md и skills. Ревьюеры запускаются
по skill `reviewer` с `fork_turns: "none"`;
каждый слепой проход review получает отдельный самодостаточный бриф, без
истории Main.

Модели ревьюеров закреплены профилями `plugins/scope-focus/agents/*.toml`:

| Профиль | Модель |
|---|---|
| `spotty` | `gpt-6.1-terra / low` |
| `bossy` | `gpt-6.1-terra / medium` |

Профили, их строки в skill `reviewer`, таблица
`install-instructions/scope-focus.md` и таблица моделей выше согласованы.
`spotty` и `bossy` имеют один промпт из `REVIEWER.md` my-pi и отличаются
только моделью и reasoning. `node tests/run.mjs` проверяет модели профилей.

### Ветки, worktree и коммиты

Каждая задача с изменениями идёт в своей ветке и своём git worktree, чтобы
одновременно работающие агенты не трогали файлы друг друга. Начинай её из
основного клона на актуальном `master`:
`git worktree add -b <task> ../my-codex-harness-worktrees/<task> master`, где
`<task>` — короткое имя задачи. Все правки задачи делаются в этом worktree.
Каждый законченный этап сразу коммитится в ветку задачи с `git add` точных
путей этапа; такие коммиты не требуют проверок, review и gate. В `master`
напрямую не коммитить. Ветка попадает в `master` только полным release по
`.agents/skills/release/SKILL.md`, всегда squash-слиянием одним коммитом. После
слияния worktree и ветка задачи удаляются.

### Обязательный gate финализации

Во время release, перед squash-слиянием в `master` и push, Main применяет
[finalize-work](.agents/skills/finalize-work/SKILL.md). Обычная сдача и коммиты
этапов в ветку задачи его не запускают. Gate состоит из сверки установленных
копий и проверки документации release. Обе проверки Main делает сам и
ревьюеров не запускает.

Сверка установленных копий сравнивает копию `model_instructions_file` с
`new-model-instructions.md`, профили в `<CODEX_HOME>/agents` с
`plugins/scope-focus/agents/*.toml` и установленную версию `scope-focus` с
manifest. Локальные правки владельца переносятся в источники, намеренные
изменения задачи ставятся по инструкциям установки. Критерий документации:
`git diff master...HEAD`, изменённые файлы и ссылки, найденные целевым поиском
изменённых имён, значений, путей и поведения; посторонний исторический дрейф
сюда не входит. Слияние и push требуют, чтобы обе проверки закончились без
открытых расхождений. Gate сам не разрешает публикацию.

### Аудит репозитория

[repo-audit](.agents/skills/repo-audit/SKILL.md) идёт только по прямому
запросу владельца на аудит; автоматически, в том числе при release, он не
запускается. Аудит проводит Bossy. Объект — весь текущий
репозиторий и каждый коммит и патч после прошлого аудита, включая промежуточные
правки, которых уже нет в итоговом diff. Main делит объект по правилу размера
из repo-audit, запускает части Bossy параллельно, исправляет принятые находки и
повторяет только затронутые части до CLEAN. Аудит, заказанный вместе с
release, стартует после обычных правок и gate финализации и не проверяет
результат, который Main ещё меняет. Критерий — согласие кода, всей
документации и принятых решений владельца, без устаревших действующих сведений,
мусора и конфликтов. Аннотированный тег `audit` указывает на последнее
проверенное состояние в `master`; дата тега — дата аудита. Тег двигается и
публикуется только после CLEAN и обычного release. Фонового таймера, файла
счётчиков, архивных копий и записей об удалении нет.

### Правила работы с исходниками

Доступность и версию моделей определяет штатный Codex. Репозиторий закрепляет
модель и effort ролей в их профилях, но не поставляет кастомный каталог
моделей.

Обычная проверка — чтение и логика. После изменений кода или конфигурации один
раз запускать существующие проверки, покрывающие изменение (`node tests/run.mjs`),
по возможности в фоне; повторять только после исправления выявленного ими сбоя.
Сбои от изменения, включая прежние утверждения о намеренно изменённом поведении,
исправлять; посторонние сбои сообщать без починки. Новые тесты, фикстуры, замеры,
опыты и проверки сверх покрывающих изменение — только по прямому запросу или
конкретно принятой процедуре. Действующий результат проверки переиспользуется
при сдаче и release, пока проверенный код, конфигурация и контракты не менялись.

Для проверочных запусков `codex exec` использовать самую дешёвую подходящую
модель: тестовый Main — `gpt-6-sol` с `model_reasoning_effort = "low"`, без
самостоятельного повышения модели или reasoning.

Сохранять пользовательские изменения. В migration без запроса не менять
location, format или value секретов.

Новая версия и установка не следуют из обычного редактирования; оно
заканчивается коммитами этапов в ветку задачи. Временные файлы задачи создаются
только во временной папке ОС, которую система очищает, поэтому их не удаляют. Слова владельца релиз, коммит, пуш и синхронизация
одинаково означают полный release одним пакетом: сверка установленных копий,
все проверки и gate finalize-work, слияние ветки задачи в `master`, push и
установка на текущем хосте. Отдельное слияние или push без остального пакета не
выполняются. Порядок release описан в `.agents/skills/release/SKILL.md`.

`INSTALL_FOR_AGENTS.md` — единая точка входа для установки и обновления.
Источники действий установки — этот входной документ, инструкция выбранного
компонента из `install-instructions/` той же ревизии и её явно указанные
зависимости. Репозиторный `AGENTS.md` описывает разработку и находится вне
процедуры установки. Компонентов два: Scope Focus
(`install-instructions/scope-focus.md`) и системный промпт
(`install-instructions/system-prompt.md`). После установки `INSTALL_FOR_AGENTS.md`
выполняет зачистку следов прежних версий по `LEGACY-CLEANUP.md`. Все
инструкции сохраняют общий
порядок разделов: состав, требования, первая установка, проверка после
установки, обновление.

Инструкции и ссылки на них не входят в plugin package, manifest, runtime skills,
hooks или профили. Системный промпт — отдельный компонент поставки, его
исходник — `new-model-instructions.md`. Прямой `codex plugin add` не выполняет
repo-level инструкции автоматически.
На этом macOS-хосте Codex CLI находится внутри Codex App: `/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex`; если команда `codex` недоступна в `PATH`, запускай этот исполняемый файл по абсолютному пути.

JSON сохранять в UTF-8 с читаемыми символами, без замены кириллицы на
Unicode-последовательности вида \uXXXX. После инструментов смены версии
сохранять этот формат, не меняя значения полей при пересериализации.

`install-instructions/*.md` и справочные тексты должны быть короткими и
содержательными.
Описывай конкретный состав, отдельно подключаемые части и готовность пакета.
В инструкции установки плагина нужны ясные шаги штатной установки и
обновления через Codex CLI, включая выбор marketplace и `codex plugin add`.
Для отдельного системного промпта указывай ключ `model_instructions_file`
в `config.toml`, реальный путь целевой машины и отличие от содержимого плагина.
Достаточные команды и примеры настроек допустимы здесь; они не переходят в
runtime skills.
Доверие к hooks устанавливается через штатный Codex app-server по текущим
определениям; обход trust запрещён. Проверки из выбранного документа
`install-instructions/*.md` выполняет
устанавливающий агент в конце установки на целевой ОС. В Windows — только
через Git Bash; результат другой ОС не доказывает работу Windows.
Редактирование исходников и документации само по себе не запускает эти
проверки. При update сохраняй данные, секреты и чужие настройки; повторяй
только требуемые проверки затронутых частей. Явный запрет пользователя на
проверочные запуски имеет приоритет. Не включай посторонние функции хоста
из-за сходства их имени с именем плагина.

Дизайн-файл `SCOPE-FOCUS-DESIGN.md` описывает действующую концепцию плагина:
назначение, подачу правил hooks и записи решений, включая синхронизацию с
my-pi. Различать предложение, согласованное решение и фактически
выполненное изменение; не приписывать согласования или результаты. Прежние версии доступны в истории Git/GitHub. Не
помещать в дизайн рабочие TODO, очереди выполнения и чек-листы релиза. Общие
правила репозитория хранятся в AGENTS.md, инструкции установки — в
`install-instructions/`.

При удалении компонента, кода или отказе от решения удаляй относящиеся к нему
действующие исходники и документацию. Не создавай архивные копии, заметки,
записи об удалении или отказе ради сохранения прошлого: для этого используется
история коммитов Git/GitHub. Оно не разрешает удалять пользовательские
данные и не отменяет документацию действующих
решений и выполненной работы.

После repo-level setup runtime-пакет plugin самодостаточен и не зависит
от документации репозитория. Установка и обновление из репозитория используют
документ выбранной ревизии. Этот файл задаёт правила работы над исходниками.

Не добавлять setup skills. Не ссылаться на рабочий репозиторий в файлах
плагина.

Системный промпт Codex — `extensions/RQW-prompt/SYSTEM.md` my-pi целиком, в
том же порядке блоков, плюс блок Communication из `extensions/RQW-dyslexia` в
конце. Отличия только в механике Codex: pi заменён на Codex, независимые
вызовы идут в один `exec` через `Promise.all`, файлы правятся только через
`apply_patch`, промежуточные сообщения идут в канал `commentary`, финальный
ответ — в канал `final`. Правила todo-списка, review, субагентов и механику инструментов подаёт
Scope Focus; механика инструментов Codex находится в skill `codex-tools`.

Всё собственное tooling проекта, включая hooks, реализуется на Node.js и
должно работать на macOS, Linux и Windows.
В Windows работать строго через Git Bash. PowerShell запрещён.
Исключение — расширение `codex-cli-vscode/`: оно запускает Git Bash через
`powershell.exe` и кроссплатформенным не является (раздел «Расширение ARQAWA
CCLI»).

## MCP и простое tooling

MCP запрещены в этом репозитории, в том числе внутри плагина и субагентов.
Не добавлять собственные MCP-серверы, клиенты, обёртки или обязательные
MCP-настройки.

Tooling строить самым простым достаточным способом: инструкции, промпты,
skills, субагенты, плагины и обычные CLI-инструменты на Node.js.
Не усложнять эту механику без прямого запроса пользователя.

## Расширение ARQAWA CCLI

`codex-cli-vscode/` — отдельное расширение VS Code `arqawa.ccli` («ARQAWA CCLI»)
для Windows `win32-x64`: оно запускает штатный Codex CLI из npm-пакета
`@openai/codex` вкладкой терминала. Цепочка запуска: extension host → `powershell.exe` →
Git Bash (`--login -i -c`) → `codex.exe`. Прокси берётся из окружения `Code.exe`
и настроек `http.proxy` / `http.proxyStrictSSL`, как у `openai.chatgpt`, и
дополнительно экспортируется в строке запуска Git Bash. `CODEX_HOME` не
меняется: настройки, вход и сессии общие с `~/.codex`. Команды: `Codex CLI: New Tab`
и `Codex CLI: Login` (`codex login --device-auth`).

Codex в VSIX не вшит. При старте VS Code расширение запускает свой встроенный
npm 10.9.9 на Node самого VS Code (`ELECTRON_RUN_AS_NODE=1`) и ставит последнюю
версию `@openai/codex` в папку `codex/<версия>/` внутри расширения; устаревшие
версии и кэш npm оно удаляет. Права администратора и ПО на хосте, кроме Git
Bash по стандартному пути, не нужны.

В Marketplace у расширения нет описания: поле `description` в
`codex-cli-vscode/package.json` не задаётся, README в папке нет.

Готовый VSIX публикуется в Visual Studio Marketplace под издателем `arqawa`
(`vsce publish --target win32-x64` из `codex-cli-vscode/`, актуальный
`@vscode/vsce` через `npx`: старая `vsce` 2.x не годится). Порядок публикации и
получение токена описаны в repo-local skill
[`publish-ccli`](.agents/skills/publish-ccli/SKILL.md): токен один раз кладёт
владелец командой `vsce login arqawa`, дальше публикует агент по прямой просьбе.
Издатель `arqawa` создаётся один раз на
`https://marketplace.visualstudio.com/manage`. Marketplace не принимает
повторную версию, поэтому перед каждой публикацией `version` в
`codex-cli-vscode/package.json` повышается.
Сборка не входит в поставку плагина, а правила tooling этого файла
(кроссплатформенность, запрет PowerShell) на расширение не действуют.
