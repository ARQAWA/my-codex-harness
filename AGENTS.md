# Рабочая база

Этот репозиторий — рабочая база текущих Scope Focus, Lunatron, каталога
моделей и системного prompt.

Источники правды после импорта:

- `plugins/scope-focus`
- `plugins/lunatron`
- `plugins/filesystem-search`
- `config/codex-model-catalog.json`
- `config/new-model-instructions.md`
- `config/INSTALL.md`
- `INSTALL_FOR_AGENTS.md`
- `install-instructions/`

Runtime-копии `~/.codex/plugins/cache` и прежние `~/plugins` отдельны.
Текущий импорт их не меняет. Дальнейшая разработка идёт здесь, установка
выполняется отдельно.

Все plugin manifest используют `0.0.0+codex.YYYYMMDDHHMMSS`; timestamp — UTC.
Для штатного bump используется `update_plugin_cachebuster.py`. Новый plugin
сразу получает этот формат. Для source release каждого изменённого plugin
выполняется один bump перед source commit. Обычное редактирование без release
и install/update без source changes версию не меняют. Timestamp вручную не
придумывать и повторный bump не делать.

## Локальная проверка исходников

Единая детерминированная проверка репозитория запускается командой
`node tests/run.mjs`. Она не заменяет install-time проверки на целевой ОС из
`install-instructions/*.md` и не меняет активный Codex home.

## Политика

Scope Focus задаёт always-on точный scope, глубокое понимание и минимальное
действие. Quality adjectives не расширяют scope.

Goal нужен только для формулирования и native goal. Task Notebook и blind review
опциональны при явном выборе. Goal Compiler и raw bundles — прежний дизайн;
в текущем составе goal skill этого нет.

### Контракт разрабатываемого Lunatron

Этот подраздел описывает поведение продукта Lunatron, а не порядок работы
агента над этим репозиторием. Он не активирует Lunatron и не предписывает
делегирование при разработке, анализе логов или редактировании исходников.
При работе над репозиторием агент выполняет задачу самостоятельно; запуск
субагентов и reviewer допускается только по прямому запросу пользователя.
Описанные ниже роли, обязательная делегация, packaged tooling и guard относятся
только к runtime-контракту разрабатываемого плагина.

Main владеет анализом, решениями, диагностикой и приёмкой; собственные сложные
патчи пишет и применяет напрямую. Main сам читает, трактует и оркестрирует
выбранные skills; помощникам передаёт уже конкретные задания, а не поручение
прочитать или исполнить skill. Явно выбранный skill-файл можно читать или
изменять как данные, но его содержимое не становится инструкцией помощнику.
Один persistent luntik отвечает только на смысловые вопросы к уже выбранным
большим данным. Обычный поиск и малые чтения Main выполняет сам. Один persistent
lunatik исполняет законченный мини-план связного блока по принятым Main решениям
и конкретным референсам. Этот внутренний мини-план автономно следует полезной
структуре Plan Mode: результат и границы; решение и референсы; действия и
зависимости; готовность, разрешённые проверки и условия возврата. Его не
показывают пользователю и не выносят на отдельное одобрение. Детализация
соответствует работе и не запускает новый исследовательский этап. Даже
короткие рабочие команды остаются у lunatik. Связанные готовые команды Main
поручает вместе с нужным порядком, зависимостями и условиями остановки.
При проблеме Main задаёт простое исправление lunatik либо сам применяет
собственный сложный патч для нужного участка.
Частые ошибки Luna не считаются установленным фактом.

Main читает решающие оригиналы с ограничением объёма вывода, а не длины команды
или числа строк. Guard 8192 байта действует только на поддерживаемые результаты
Main; собственный вывод помощников им не ограничивается. Ответ Luna для Main
краткий, но сохраняет существенные факты, источники, ошибки, противоречия и
неизвестное. Один final без дублирующего send и ожидания после итога.
Полный автоматический перехват сообщений V2 текущим hook не обеспечивается.

Luntik читает выбранные Main большие файлы или сохранённые результаты и отвечает
на один конкретный смысловой вопрос. Он возвращает краткие факты и точные места
для решающего чтения Main, но не ищет по репозиторию и не выбирает источники,
стратегию, диагноз или решение. Packaged tooling сохраняет полный вывод заранее
выбранных потенциально больших команд, извлекает диапазоны и JSON Pointer и
делает ограниченный буквальный поиск. Luntik нужен только после механического
сужения, когда данным требуется смысловая интерпретация.

После готовности связного блока Main сам проверяет и принимает работу.
Main читает решающие оригиналы, сверяет результат с исходным поручением
и поручает необходимые исправления. Отчёт помощника не заменяет эту проверку.

В packaged profiles сейчас указаны:

- `lunatik`: `gpt-5.6-luna/max`
- `luntik`: `gpt-5.6-luna/max`

Исторические значения не переносить.

### Правила работы с исходниками

Каталог содержит видимые `gpt-6-astra`, `gpt-5.6-sol`, `gpt-5.6-terra`,
`gpt-5.6-luna` и скрытые `gpt-reserve`, `codex-auto-review`. Настройки читать из JSON. Старые
значения из истории не переносить.

Общая execution policy работает без Goal. Единственное runtime-состояние
управления Lunatron — заказанный файл режима `ltn` текущей задачи. Не добавлять
другой router, state, toggle или enforcement вместо prompt.

Обычная проверка — чтение и логика. Эмпирические проверки выполнять только по
прямому запросу или конкретно принятой процедуре.

Для проверочных запусков Lunatron использовать самую дешёвую подходящую
модель: тестовый Main — `gpt-5.6-sol` с `model_reasoning_effort = "low"`.
Не запускать для этих проверок Astra и не повышать модель или reasoning
самостоятельно. Luntik и Lunatik используют профили проверяемой версии.

Сохранять пользовательские изменения. В migration без запроса не менять
location, format или value секретов.

Tritron и Lunatron не смешивать в runtime. Tritron не входит в этот snapshot.
В автоматическом режиме Lunatron активируется у root только для `gpt-5.6-sol`
и `gpt-6-astra`; `gpt-5.5`, `gpt-5.6-terra` и `gpt-5.6-luna` его не активируют.
Reasoning и transcript не участвуют. Точные корневые команды `ltn 1` и `ltn 0`
принудительно включают или выключают Lunatron в текущей задаче независимо от
модели; `ltn -1` удаляет override и сразу возвращает автоматику текущей модели.
Плагин и hooks остаются включёнными, иначе команды режима недоступны.
Независимо от `ltn`, общий PostToolUse guard защищает root
`gpt-5.6-terra`, `gpt-5.6-sol` и `gpt-6-astra`: большой поддерживаемый результат
сохраняется и заменяется коротким сообщением через `continue:false`. Это не
означает полный перехват hosted WebSearch, V2-сообщений или каналов без hook.

Новая версия, установка и cleanup не следуют из обычного редактирования.
Порядок release описан в `.agents/skills/release/SKILL.md`.

`INSTALL_FOR_AGENTS.md` — единая точка входа для установки и обновления.
Установщик читает корневой `AGENTS.md`, выбирает ровно один основной plugin из
запроса и выполняет его документ из `install-instructions/` той же ревизии.
Установка и обновление `filesystem-search` обязаны поддерживать
управляемый глобальный блок маршрутизации в активном
`<active-codex-home>/AGENTS.md`; его единственный source of truth и алгоритм
синхронизации находятся в `install-instructions/filesystem-search.md`.
Документы других плагинов разрешено читать и выполнять только в части явно
объявленных обязательных зависимостей выбранного plugin. Уже подготовленные
совместимые зависимости переиспользуются; остальные функции и полная установка
другого plugin автоматически не запускаются:
`scope-focus.md`, `lunatron.md` или `filesystem-search.md`. Все три документа
сохраняют общий порядок разделов: состав, требования, первая установка,
проверка после установки, обновление.

Инструкции и ссылки на них не входят в plugin package, manifest, runtime skills,
hooks или обычные runtime-инструкции. `config/INSTALL.md` остаётся отдельным
документом для model catalog и общих model instructions. Прямой `codex plugin
add` не выполняет repo-level инструкции автоматически.

JSON сохранять в UTF-8 с читаемыми символами, без замены кириллицы на
Unicode-последовательности вида \uXXXX. После инструментов смены версии
сохранять этот формат, не меняя значения полей при пересериализации.

`install-instructions/*.md` и справочные тексты должны быть короткими и
содержательными.
Описывай конкретный состав, отдельно подключаемые части и готовность пакета.
В каждом `install-instructions/*.md` нужны ясные шаги штатной установки и
обновления через Codex CLI, включая выбор marketplace и `codex plugin add`.
Для отдельно поставленных custom catalog и общих instructions указывай точные
ключи `model_catalog_json` и `model_instructions_file` в `config.toml`, реальные
пути целевой машины и отличие этих компонентов от содержимого пакета.
Достаточные команды и примеры настроек допустимы здесь; они не переходят в
runtime skills.
Доверие к hooks устанавливается через штатный Codex app-server по текущим
определениям; обход trust запрещён. Проверки из выбранного документа
`install-instructions/*.md` выполняет
устанавливающий агент в конце установки на целевой ОС. В Windows — только
через Git Bash; результат другой ОС не доказывает работу Windows.
Редактирование исходников и документации само по себе не запускает эти
проверки. При update сохраняй данные, секреты и чужие настройки; повторяй
только требуемые проверки затронутых частей. Явный запрет пользователя на
проверочные запуски имеет приоритет. Не включай посторонние функции хоста
из-за сходства их имени с именем плагина.

Дизайн-файл каждого плагина описывает только этот плагин и его необходимые внешние контракты. Не помещать план, требования реализации или правки одного плагина в дизайн другого. Общие правила репозитория хранятся в AGENTS.md. При совместном апгрейде отдельно сверять взаимодействие плагинов в рамках заказанного объёма и выбранной процедуры; раздельная приёмка каждого плагина не заменяет эту сверку.

Дизайн-файл хранит концепцию плагина и историю его проектирования: назначение, проблемы, исходный контекст, предложения, принятые и отклонённые решения, согласования пользователя и причины изменений. Он должен объяснять, почему плагин устроен именно так. Различать предложение, согласованное решение и фактически выполненное изменение; не приписывать согласования или результаты. Сохранять значимую прежнюю историю при обновлении, помечая заменённые решения как исторические. Не помещать в дизайн рабочие TODO, очереди выполнения и чек-листы релиза. Текущий план и статус работы ведутся в выбранном Task Notebook; текущие инструкции установки находятся в соответствующем `install-instructions/<plugin>.md`.

После repo-level setup runtime-пакет каждого plugin самодостаточен и не зависит
от документации репозитория. Установка и обновление из репозитория используют
документ выбранной ревизии. Этот файл задаёт правила работы над исходниками.

Не добавлять setup skills. Не ссылаться на рабочий репозиторий в файлах
плагинов.

Общие инструкции модели описывают поведение и принципы работы без привязки к
конкретным функциям, командам и переменным окружения.

Всё собственное tooling проекта, включая hooks, реализуется на Node.js
и должно работать на macOS, Linux и Windows.
В Windows работать строго через Git Bash. PowerShell запрещён.

## Запрет MCP и простое tooling

Любые MCP в любом виде полностью запрещены в этом репозитории.
Не создавать, не подключать, не использовать и не требовать MCP-серверы,
MCP-клиенты, MCP-обёртки или MCP-интеграции с Codex и harness.
Запрет действует также внутри плагинов и субагентов. Не добавлять обязательные
MCP-зависимости и MCP-настройки, затрагивающие весь хост.

Tooling строить самым простым достаточным способом: инструкции, промпты,
skills, субагенты, плагины и обычные CLI-инструменты на Node.js.
Не усложнять эту механику без прямого запроса пользователя.

## Что означает кастомный каталог моделей

- Основа — дефолтная запись каждой целевой модели из одного установленного
  источника каталога. Astra служит донором только механических возможностей
  взаимодействия с harness; полное клонирование записи Astra запрещено.
- Сохранять индивидуальные свойства модели: slug, имя/описание, базовый prompt
  и personality, список и default effort, весь fast/service-tier режим и его
  описания, лимиты context_window/max_context_window, модальности, модельные
  ограничения и API-доступность. Отсутствие ключа, null и пустое значение не
  считать взаимозаменяемыми.
- Из Astra переносить только явно выделенные harness-поля: протоколы
  shell/apply_patch/web-search, доступные синхронные/асинхронные инструменты,
  Node REPL и его review, tool_mode,
  multi_agent_version/multi_agent_reasoning_effort, управление
  бюджетом/усечением контекста, approvals, collaboration modes и прочие
  отдельные технические model_messages. Клиентский transport use_responses_lite
  относится к этому слою; перенос не доказывает серверную совместимость.
- Контекст разделять: физические лимиты модели сохраняются;
  truncation_policy, effective_context_window_percent и технические
  token_budget/compaction-инструкции берутся у Astra. Не увеличивать лимиты
  модели вслед за донором.
- Смешанные инструкции не копировать целиком: сохранять личный текст модели;
  заменять только явно определённые технические фрагменты о протоколах
  инструментов/контекста. Отдельный model_instructions_file не менять без
  прямого запроса.
- Перед переносом фиксировать явный список JSON-полей/фрагментов для
  копирования. Неизвестные или неоднозначные поля (например, непрозрачный
  comp_hash без подтверждённого смысла) сохранять у получателя до выяснения
  назначения; не выводить смысл только из имени и не копировать все оставшиеся
  поля по умолчанию.
- visibility и priority задаются отдельно по запросу владельца. Визуально
  скрытая модель остаётся записью каталога; скрытие не означает удаление или
  запрет служебного использования.
- Для текущего проекта получатели: gpt-6-astra, gpt-5.6-sol, gpt-5.6-terra,
  gpt-5.6-luna. Порядок видимых: gpt-6-astra, gpt-5.6-sol,
  gpt-5.6-terra, gpt-5.6-luna. Остальные модели скрыты. Это целевое состояние
  проекта, не утверждение о выполненной установке.
- Кроссплатформенность macOS/Linux/Windows обязательна: обычный JSON и штатные
  пути/механизмы хоста; не переносить абсолютные пути одной ОС в другую.
  В Windows команды установки документируются только для Git Bash.
