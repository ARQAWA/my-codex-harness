# Filesystem-search: платформенные маршруты и установка

## Основание и статус

Требование принято после сообщения пользователя с отчётом о native Windows 11
и последующего уточнения: текущая механика и установка macOS/Linux работают и
должны сохраниться; для Windows нужна отдельная установка и маршрут. Этот
контракт заменяет прежнее предположение об одной общей схеме для всех ОС.

## Действующий контракт

Плагин сохраняет имя `filesystem-search`, существующий marketplace entry,
skills path, author, интерфейс, capabilities и два зарегистрированных hook.
Плагин сам не устанавливает, не запускает и не настраивает внешние MCP.

### macOS и Linux

Сохранить текущую механику и установку без замены инструментов:

- известный точный файл читать напрямую;
- CBM MCP использовать для кода, символов, вызовов, зависимостей и связей;
- `tgrep` MCP использовать для текста, имён файлов, документации и
  конфигурации;
- `ast-grep` MCP использовать для структурного поиска синтаксиса;
- свежие, отрицательные и полные утверждения проверять по текущим исходникам
  или узким границам поиска; для явного `index_repository` задавать
  `persistence: false`.

Действующая инструкция находится в `install-instructions/filesystem-search.md`.
Её схема MCP, значения пользовательских кэшей и обновление не меняются.

### Native Windows 11

Известный точный путь читать напрямую; текст искать командой `rg -n`, имена
файлов — `rg --files`. Для символов, вызовов, зависимостей, impact и отношений
использовать внешний CBM MCP: `search_graph` подтверждать через `trace_path`
либо ограниченный graph query. Для структурного синтаксиса использовать
внешний `ast-grep` MCP (`find_code` или эквивалент). Совпадения `rg` не являются
доказательством графовой связи или AST.

Если MCP отсутствует, handshake не прошёл или конкретный вызов завершился
ошибкой, назвать недоступную функцию. Применять `rg` и прямое чтение только там,
где они действительно отвечают на вопрос. Граф может быть неполным или
устаревшим; свежие, отрицательные и полные выводы сверять с текущими файлами и
границами поиска, учитывая hidden/ignore, если это влияет на полноту.

Пользовательская настройка CBM задаёт `auto_index = true`; обычный поиск не
требует подготовительного `index_repository`. При явно вызванном
`index_repository` передаётся `persistence: false`. Граф хранится в кэше CBM
пользователя; плагин не создаёт проектный `.codebase-memory/graph.db.zst`.
`ast-grep` не требует постоянного текстового индекса. Оба сервера — отдельные
процессы, регистрируемые Codex-инсталляцией пользователя.

Windows-установка описана отдельно в
`install-instructions/filesystem-search-windows.md`. Она использует pinned
ast-grep MCP commit и `--with ast-grep-cli`, не регистрирует `tgrep` и не
наследует параметры запуска, подтверждённые только на одной VDI, как
универсальные настройки. Повторяемый сбой CBM требует диагностики stderr и
условий запуска этого сервера; регистрация MCP или единичный успешный вызов не
доказывают постоянную готовность.

### Hooks и границы реализации

Существующие `SessionStart` с matcher
`^(startup|resume|clear|compact)$` и `SubagentStart` вызывают через Node модуль
`hooks/search-context.cjs` из `PLUGIN_ROOT`; timeout обоих command-hook — 7.
Модуль по `process.platform === 'win32'` печатает краткий маршрут платформы
через `process.stdout.write(lines.join('\n'))`. Он не ищет, не индексирует,
не запускает MCP/процессы и не блокирует инструменты.

Не добавлять собственные daemon, watcher, lock, root guard, server wrapper,
проектный индекс или ветвление процесса поиска. Не удалять пользовательские
кэши, проектные данные или не принадлежащие этой установке записи. В plugin
manifest описывать оба маршрута без обещания единого backend для поиска текста.

## Установка и миграция Windows

Сначала проверять активный Codex binary/config и реальные команды/API его
версии: запись `codex` в `PATH` может относиться к другой установке. Проверять
серверы независимо: существующую запись проверять и при необходимости исправлять
только для этого сервера; отсутствующую добавлять только соответствующей ей
командой ниже. Никогда не повторять регистрацию уже существующего сервера.
Точные команды регистрации:

```bash
codex mcp add codebase-memory-mcp -- uvx --from codebase-memory-mcp codebase-memory-mcp
codex mcp add ast-grep -- uvx --from git+https://github.com/ast-grep/ast-grep-mcp@149e20d47bb7125fb0c1451feea2f48a98742034 --with ast-grep-cli ast-grep-server
```

До регистрации CBM проверить пакет через `--version`, задать `config set
auto_index true` и проверить `config get auto_index`. Первичная загрузка требует
сети. `UV_OFFLINE=1` допустим только как необязательная настройка сервера после
полного прогрева pinned-пакета с `ast-grep-cli`.

На проверенной VDI наблюдались `mcp_optional_startup_grace_ms = 0` и
`startup_timeout_sec = 30` у обоих серверов; позже в новой задаче CBM снова
завершился с `connection closed: initialize response`. Эти значения не
являются универсальным рецептом и не доказывают исправление CBM. Hook hashes
получаются через app-server `hooks/list`, trust и enabled настраиваются через
`config/batchWrite` по текущим определениям.

Удалять старый managed-блок `FILESYSTEM_SEARCH_GLOBAL_ROUTING` из активного
`AGENTS.md` только если найден ровно один полный блок с обеими границами; при
неполных или повторных маркерах прекратить это удаление и сообщить о конфликте.
Старую запись `tgrep` удалять только при подтверждённой принадлежности данной
Windows-установке filesystem-search.

## Приёмка

1. Текущие skill и hook явно сохраняют маршрут CBM + `tgrep` + `ast-grep` для
   macOS/Linux и задают `rg` + CBM + `ast-grep` для Windows; `tgrep` отсутствует
   именно в действующем Windows-маршруте.
2. Manifest, marketplace entry, две hook-регистрации и interface identity
   сохранены; Windows-hook только выводит routing context.
3. Отдельная Windows-инструкция содержит точные команды pinned серверов,
   настройку CBM auto-index, условия миграции и честные ограничения наблюдений.
4. Consistency test проверяет согласованность исходников и документации для
   обеих ОС. Успешное статическое тестирование не считается Windows runtime
   проверкой.
5. Для runtime-приёмки Windows нужна новая Codex-задача, в которой реально
   вызваны `rg -n`, `rg --files`, CBM graph-инструменты и ast-grep `find_code`,
   доставлены оба context hook и проверено отсутствие нового проектного
   `.codebase-memory/graph.db.zst`. Список конфигурации или ручной initialize
   вместо этих вызовов не засчитывается.
