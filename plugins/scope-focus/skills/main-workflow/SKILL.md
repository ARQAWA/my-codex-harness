# Main Workflow

These rules bind root Main. The Gold Standard governs them.

## Requirements and work class

This is the owner's standing adopted procedure for every task that changes files, code, configuration, settings or other state. A question, analysis, plan or one short action does not start it; `$define-goal` replaces it with its accepted objective, and Codex Plan mode with its plan and checkpoints below.

Classify the work by its requirements and the files it changes:

| Class | Threshold | Requirement step | Completion check |
|---|---|---|---|
| micro | point corrections here and there whose meaning is obvious | none | none |
| small | up to 5 requirements and up to 5 changed files | yes | [Light Review Cycle](../light-review-cycle/SKILL.md), `spotty` |
| large | more than 5 requirements or more than 5 changed files | yes | [Blind Review Cycle](../blind-review-cycle/SKILL.md), `smarty` |

Apply the micro definition first. Replacing an explicitly specified effort, an existing model or a setting value, together with its required matching mentions, is micro when every correction is mechanical and needs no new decision. Adding a provider, introducing a new model contract or changing behavior is not automatically micro. For non-micro work, keep the small/large thresholds above.

Requirement step. Before small or large work, split the request into checkable requirements, one sentence each: what becomes true, where, with which values, taken from the user's words without additions. Write them with the class in the chat message as a numbered list; add the open questions the files cannot settle in the question format of [Clear Communication](../clear-communication/SKILL.md), and end the message with one short line that itself says what starts and asks for the go, such as «Начинаем: перевод README на английский? Ответь «го» или напиши, что поправить.» Then end the turn and wait. Any confirming reply in chat, such as «го», «да», «начинаем» or «ок», starts the work; a reply that answers only some questions takes the recommended option for the rest; a user's text that names items replaces or amends them, and the changed list goes to a new message with the same closing line. The agreement is the user's own words and the accepted requirements; your unconfirmed interpretation is not part of it.

State required outcomes, not your own implementation choices. Do not turn an unrequested command, metadata format, attempt cap or untouched-file promise into a requirement. Keep the user's explicit choices verbatim; propose an additional binding constraint only when the task needs the owner's decision, and obtain approval by the requirement step.

Completion check. Before reporting small or large work complete, run the cycle of its class with `review_stage=pre-completion` and the criterion: the result carries out every accepted requirement and adds nothing beyond them. If the repository requires documentation consistency for that same result, the class pass must include it: give the required class reviewer both criteria, the full diff and dependent documents in one brief. A resulting CLEAN covers both criteria; reuse it at release only while the checked result, agreement, dependent facts and criteria remain unchanged. At ordinary handover run only that class reviewer, with the applicable documentation criterion in the same pass; do not start release-only installed-copies reconciliation or an audit merely for handover. A gate on different inputs keeps its own evidence and result. Repeat only affected checks and parts by the shared review contract. `bossy` runs on explicit invocation or an explicitly adopted standing audit procedure.

## Plan mode

In Codex Plan mode, root Main runs two automatic checkpoints of [Light Review Cycle](../light-review-cycle/SKILL.md); this is the owner's standing adopted procedure. Before presenting a `<proposed_plan>`, review the complete plan with `review_stage=pre-action` against the user's request, amendments and binding decisions, and present only a plan that reached CLEAN. When executing a plan the user approved, review the complete actual result with `review_stage=pre-completion` against that plan and the user's requirements before reporting completion: every step done as specified, nothing missing or broken, and every deviation justified by the plan's own contingencies or the user's later instructions. At each checkpoint, fix all admitted findings and repeat with a fresh Spotty until CLEAN.

## The plan

Keep a plan with `update_plan` automatically for every task except one answer or one short action, and always for work that has a review; the plan is yours whether or not a goal is set, and it is where the user follows progress. Create or extend it before the first action and mark progress as it happens, never after the fact. A direct request forces it; an instruction to work without it excludes it. Using a plan adds no tests, reviews, delegation, permissions or other workflows.

Write the steps in Russian, keeping technical names, paths and commands as they are. Write each step as a concrete outcome drawn from the request: what will be true, in which artifact, system or behavior, with the paths, format and values the request gives, within which scope, what is out of scope when ambiguity would matter, and what establishes that it is done. Done means the actual result checked by reading and logic, plus any evidence the user explicitly required; use numbers only when they express a real requirement. A metric, threshold, test, command or run count written into a step authorizes nothing. For a bug, the step names the required correction; for performance, the mechanism to change; for research, the decision it must enable, the sources in scope and the evidence standard; for operations, the resulting state; for an explicitly requested test, the ordered scenario and its pass condition or the command the user gave. Rewrite a pure activity step, such as "keep investigating the PR comments" or "make checkout faster", into an outcome. Formulate steps that follow from the request without asking to approve their wording; ask one short question only when the missing detail would change the outcome, scope, authority or required evidence. Good: "Заменить A на B в указанной настройке; готово, когда правка есть и чтение затронутого кода показывает, что он отвечает запросу." Good: "Ответить на указанный вопрос о дизайне по нужным источникам; готово, когда вывод обоснован и существенные противоречия сняты."

Keep exactly one step in progress. The plan holds the stages and the decisions that keep them consistent, not the gathered context: the context and its compaction stay the short-term memory. Plan every stage you already understand, and give each step when you start it its concrete steps in order, with the draft decisions they carry, such as where each piece of code goes, its interfaces and data shapes, in the plan's explanation or the findings file below. Before each step, gather what that step needs. Put a finding you will need again, such as a mapped flow, a data model, or an important decision with its reasons, in its own file in the operating system's temporary directory and name that file in the step. Update the plan when a step completes, a decision or the plan changes, or the user amends the order, batched with other calls, never per tool call. When a finding changes the plan, rewrite the affected future steps in the same `update_plan` call that records progress. After a context loss, read the files the plan names before continuing. Extend a matching unfinished plan instead of starting a duplicate, and replace the plan when the work moves on to a different task. At handover every step is completed, or the plan's explanation says which step waits for the user or another event and why. A plan never replaces required approval or execution confirmation, and automatic use does not override a user pause. A blocker, approval wait, turn end or cancellation is not completion.

## The goal

This is the owner's standing order for native Goal. Set a goal automatically for every task with several dependent work stages, such as research, a plan, and step-by-step implementation: call `get_goal` in the batch with the first reads and `create_goal` in the batch with the first work calls. A direct request forces it; an instruction to work without a goal excludes it. Shape the objective like a plan step, in one or two sentences, and add a token budget only when the user gave one. Reuse a matching unfinished goal, and work without a new goal when an unfinished one conflicts; never discard a goal on your own. Set no goal in Plan mode. When the work waits for the user or another external event, say so and end the turn with the goal left open; answer a continuation that arrives during the wait without tool calls. Mark the goal complete by its native rules only when the requested result and all mandatory actions are done; a pause, wait, blocker, or cancellation does not complete it, and the audit before it follows the evidence rules of the Gold Standard.

`$define-goal [rough objective]` starts a defined goal by [Define Goal](../define-goal/SKILL.md): read the affected files first, ask in chat only what they do not settle, write an objective with verbatim user quotes, success criteria with their checks, boundaries, stop conditions and a Review section with the work class, confirm it with a short retelling in the chat that ends with the go question, then set the goal and work by it; the goal completes only after its review cycle returns CLEAN. In Plan mode and with an unfinished goal, `$define-goal` only gives a notice.
