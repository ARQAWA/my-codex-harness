# Codex tool mechanics

- Code mode cuts every `exec` result to 10,000 estimated tokens: 40,000 bytes, which is about 40,000 characters of code or English text and about 22,000 of Cyrillic. The cut removes the middle and keeps the head and tail. Only the first-line pragma of the `exec` raises this limit; `max_output_tokens` on nested calls does not.
- Begin every `exec` that reads files or searches with `// @exec: {"max_output_tokens": N}`, where N covers everything the script emits (100000 when unsure), and give each nested `exec_command` the same `max_output_tokens`. Control volume by choosing what to read. Keep default limits for builds, tests, and logs, and filter their output.
- The context window holds about 258,000 tokens, about 40,000 of them taken at task start. Code takes about two-thirds of the reader's estimate of one token per four bytes. Size only the paths the task needs with `--sizes`, never a listing of a whole large repository. When those paths plus the deliverable stay under about 150,000 real tokens, read everything yourself and write once; otherwise read what fits, because a full context triggers a slow compaction and rereading.
- Read files with the reader CLI whose path the hook supplies. `--sizes` lists directory totals in tokens, and `--files` lists files instead. A plain call prints a file of up to 1000 lines whole; a longer file prints its first 1000 lines and the exact `--lines` argument to continue from. Content over 100,000 characters fails with a request to read a range with `--lines` or to search with `rg`. Several files in one call are printed whole up to `--budget` tokens (default 90,000, at most 200,000; raise the pragma with it), and the output ends with the exact `--from` argument for the next part, so nothing is cut silently. Read every file that may relate to the subject in one call. `--skip-tests` leaves out test files and Rust test modules, `--lines A-B` prints a window of one file, and `-n` numbers lines.
- Optimize for the fastest result first and the fewest turns second: a whole-file read or a project-wide search costs seconds, and one extra turn costs far more. Put every call that does not need another call's output into the current step: independent reads, searches, listings, commands, and queries in one `exec`, started together and awaited with `Promise.all`, and independent direct tool calls, such as `spawn_agent`, in one response. Await one call before starting another, and use separate turns, only when one call's output determines the next call's input or when they could conflict, such as two patches to the same file. Reduce results in JavaScript and emit only what the next decision needs, such as `text(r.output)`.
- Search greedily in waves, broad first, then narrower. First `exec`: several broad `rg` searches in parallel, without a match limit, one per facet of the subject, each putting every name, synonym and spelling into one alternation, plus `rg --files -g` for the deploy, run and entrypoint files (compose, Dockerfile, Makefile, systemd, CI, main, bin, __main__). Each next `exec`, in one batch: read whole, with the reader CLI, the files whose matching lines show a definition, configuration or entrypoint of the subject, and those run files; read other hits only around their matching lines with `--lines`; continue longer files from the returned line; and search the exact identifiers just found. Stop when every part of the question has an answer backed by a file and line, covering every implementation, caller and config key of the subject itself; do not follow the subject into neighbouring subsystems the question does not ask about.
- `rg` respects `.gitignore`. Prefer `-t` over a broad `-g`; wildcard globs such as `*` bypass ignore rules and slow searches. Escape regex metacharacters. Use `-U --multiline-dotall` only when a match spans lines. Emit at most the first 51,200 characters of each search result; when a result is cut, say so to yourself and tighten the pattern instead of reading on.
- Never use `exec` JavaScript to search or read code while gathering context: `rg` and the reader CLI do that. Use JavaScript for computation, data processing, or filtering the output of many calls: counts, totals, tables, joins of several sources, such as applying migrations in order or checking which config keys the code reads; one `exec` reads the files and emits only the result.
- Never guess what a tool can establish: when unsure about file content, code structure, configuration, behavior, or an external item, read it or search for it.
- Do not restate raw tool output. Do not reread a file after a successful patch to confirm it.
- A result that shows `tokens truncated` has lost its middle. Request only the missing part with a larger limit before relying on it.
- One completed `wait_agent` can deliver several answers. Count the answers, and stop waiting once every spawned agent has answered.
- A turn has an output limit: write a file longer than about 400 lines in parts, the first part with Add File and the rest appended with Update File, so one call never runs into the limit and loses the turn.
- Put long text for `exec` JavaScript, such as a document, patch, or script, in a block comment and read it back, so nothing in it needs escaping: write `const doc = (() => {/*` on one line, the text verbatim on the following lines, and `*/}).toString().split("\n").slice(1, -1).join("\n") + "\n";` on the line after it. Write a `*/` inside the text as `*\/` and restore it with `.replaceAll("*\\/", "*/")`. Never put long text in a template literal or a quoted string: one unescaped backtick, `${`, quote, or raw line break fails the script and loses the text. `exec` has no Node APIs: no `btoa`, `Buffer`, `require`, `fs`, or `console`.
- Write files only with `tools.apply_patch`, never with shell redirection, heredoc, `node -e`, or `python`. Create or fully rewrite a file with one `*** Add File: PATH` whose lines come from `doc.split("\n").slice(0, -1).map(l => "+" + l).join("\n")`; Add File overwrites an existing file, so never pair it with Delete File. One patch names each path once. Append a long document in parts of a few thousand tokens: Add File for the first part, then `*** Update File: PATH` with a `@@` hunk of only `+` lines for each next part. For an edit, copy every context and `-` line verbatim and contiguous from a read of that file made after its last change and after the last compaction, without line numbers; otherwise read that region again first. Prefix every hunk line with space, `-`, or `+`.
- `apply_patch` has no `workdir`: a relative path resolves against the session directory. Give a file outside it, such as a temporary file or another repository, as an absolute path in the operating system's form: `/Users/...` on macOS, `C:/...` on Windows, never `/c/...`.
- Call a command in this shape: `const cmd = ...;` on its own line, then `const r = await tools.exec_command({ cmd, workdir, max_output_tokens: N });`, then emit `r.exit_code` with the output you need. Never close the options object inside or right after the command text. `workdir` must be an existing directory.
- Write commands that run the same in zsh on macOS and in bash from Git Bash on Windows. Quote every glob, or list files with `git ls-files` or `rg --files -g`, because an unmatched glob aborts zsh. Never name a shell variable `status` or `path`, and never start a word with `=`. Avoid flags that exist only in BSD or only in GNU tools: `find -printf`, `sed -i`, `date -d`, `readlink -f`, `stat -c`/`-f`, `timeout`. Do not use `jq` or `python`, which Git Bash lacks. Never nest a script inside a quoted command, such as `ssh`, `bash -c`, or a heredoc for an interpreter: write the script to a temporary `.mjs` file in the operating system's temporary directory with `apply_patch`, and run `node FILE`.
- Filter, slice, count, and parse output in JavaScript instead of `jq`, `awk`, or `sed` scripts. Call `JSON.parse` only on text known to be JSON, inside `try`.
- Delete with plain `rm` or `rm -r`, never with `-f`: Codex rejects a command with a forced removal, including everything else in that command.
- Use only paths taken from a listing, a search, the reader CLI, or the hook. Never rebuild a versioned plugin cache path or a remembered path from another machine. When a path may be absent, list its directory first.
- For a long run, set `yield_time_ms` in the `exec` pragma to the expected duration, and give `wait` a `yield_time_ms` that covers the expected remaining time. Never poll a running command or agent. `yield_time_ms` on `exec_command` affects only that command. Send `write_stdin` only to a `session_id` that is still running.
- Never declare a variable named `tools`. Find a deferred tool's exact name in `ALL_TOOLS` before calling it.
