# 02. Составить двухслойную спецификацию

Вход: запрос и основания U/F/Q из разведки.
Теперь прочитай [шаблон спецификации](../templates/spec.md).
Создай или уточни `spec.md`; статус — `ЧЕРНОВИК`, версия — `v1` либо следующая
после смыслового изменения уже показанного текста.

Сначала опиши простое решение на уровне конечного поведения. Не требуй от
пользователя заранее знать способ реализации. Отделяй требования `R-001`,
критерии приёмки `AC-001` и решения `D-001`.

Для каждого существенного решения зафиксируй один вид:

- `ПРЯМОЕ`: пользователь явно выбрал это; есть U-источник.
- `ВЫНУЖДЕННОЕ`: при действующих требованиях и обязательных ограничениях другой
  допустимый вариант отсутствует. Назови основания и короткое объяснение.
  Наличие готовой библиотеки или текущего паттерна само по себе этого не доказывает.
- `ВЫБОР`: допустимо несколько вариантов. Выбери самый простой достаточный внутри
  задачи; укажи реальную альтернативу и короткую причину выбора. Это решение
  агента для согласования, а не ранее данное указание пользователя.

В человеческой части покажи существенный ВЫБОР формой:
«Неоднозначно: … Решил: … Причина: … Можно изменить: …».
Рутинные технические подробности оставь агенту. При нескольких влияющих на
результат выборах обсуждай их короткими порциями, не прячь их ради лимита текста.
Выбор, меняющий объём, стоимость, доступ, приватность либо необратимое действие,
не считай рутинным: обозначь его для явного решения пользователя.

В черновике R может ссылаться на U либо на D, необходимое для достижения U.
Второй случай явно помечай как предложенный до согласования. Решение должно
уточнять средство или результат внутри поручения, а не создавать соседнюю задачу.
F подтверждает факт или ограничение, но не заменяет U как основание желаемого
результата. Неприменимость идеи не равна пользовательскому запрету.

Человеческая часть: ориентир 5–7 коротких строк, простые слова. Она объясняет
проблему, результат, границы, важный выбор и признак готовности. Число строк —
ориентир оформления, не разрешение скрыть существенную неопределённость.

Агентская часть: все существенные условия именно этой задачи. Для каждого R
задай наблюдаемое поведение, вход/условие, результат и AC. Опиши относящиеся
к задаче данные, интерфейсы, ошибки, ограничения и примеры в объёме, нужном
для однозначной реализации. У каждого спорного места есть D либо Q.
Существующие контракты можно цитировать ссылкой; не копируй весь код.

Не добавляй лимиты, сроки, формат, безопасность, миграции, архитектуру, тесты
или обработку редких случаев «для надёжности». Конкретная деталь допустима,
когда её требует запрос, действующий обязательный контракт либо необходимое
и явно обозначенное решение внутри задачи. Иначе удали её или вынеси вопрос.
Измеримость не требует выдуманного числа: успех можно описать наблюдаемым исходом.
Приоритеты сценариев задавай только когда они действительно влияют на заказ;
не придумывай продуктовый roadmap.

До согласования нет плана, порядка правок и списка задач. Карта найденных
компонентов — контекст, не предписание редактировать каждый из них.
Не превращай пример с условными данными в новое обязательное значение.

Выход: обе части согласованы между собой, основания доступны, все решения
классифицированы, неизвестное обозначено. Открой `03-decision-check.md`.
