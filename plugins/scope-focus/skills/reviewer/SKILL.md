# Reviewer

Blind review by a separate read-only model that works with you as one team for the user's agreement: it checks the requested criterion, including checks beyond the agreement and exclusions, and gets the user's own messages verbatim. Use it when the user asks for a review or a checked result: his skills `$blindreview` and `$highreview` ask for these levels, and a skill he calls may run it as its procedure. Never launch a reviewer on your own initiative or as an automatic step of other work. Keep working meanwhile, but leave the reviewed files unchanged until its verdict.

- Level: blind by default; high when the user asks for it. The level picks the profile: blind `spotty` (`gpt-6.1-terra` low), high `bossy` (`gpt-6.1-terra` medium). Launch a fresh agent for the initial review and for each changed-object pass with `spawn_agent`, `agent_type` set to that profile and `fork_turns: "none"`; the profile pins the model and carries the reviewer role, and the brief is the reviewer's whole input, with every path absolute when the work runs in another directory. If the selected profile is unavailable, report that the reviewer cannot run. There is no standalone review tool or fallback.
- The launch returns at once and the verdict arrives later as that agent's final message. Keep doing your own part meanwhile; when nothing else is left, call `wait_agent`, and finals wake you. Never poll and never run filler commands.
- Brief, these sections in this order. Supply primary requirement and governing-rule sources, not only your summary; the reviewer reads them independently, including any required user-facing explanation rules:
  - `<user_messages>`: every message of the user in this conversation, verbatim and in order, each as `<message n="N">…</message>`; a summary of earlier context goes in as `<compaction_summary note="written by the main model when it compacted the context, not the user's words">…</compaction_summary>`.
  - `<agreement>`, only when needed: only decisions the user himself accepted, verbatim, each with its source and evidence of his acceptance. Your approval or another agent's is not agreement.
  - `<object>`: exact paths or readable references to the object, primary requirements, applicable governing rules and source evidence, the diff as a file path, and the stage: pre-action or pre-completion; use the saved rules for a versioned workflow.
  - `<criterion>`: what this check confirms and which deliverable must fulfill each obligation; an exclusion cannot silently waive a governing requirement of this pass. Always include: "Any element beyond the user's requirements and decisions the user himself accepted is a finding."
  - `<rejected_earlier>`, from a changed-object pass on: the findings rejected in earlier passes, each with its reason.
- Do not impose file, search, tool-call or turn quotas on a reviewer. Read-only inspection may take as many calls as the in-scope check needs; large or truncated sources are read in complete parts.
- The verdict comes as the reviewer's final:
  - `CLEAN` with concise concrete `CHECKED:` evidence and no `UNCHECKED:`: this pass passed. Evidence names what was inspected and the exact files, sections or source anchors that establish it; it is not a long per-obligation checklist. Run no extra pass for confidence, but preserve every independent pass required by the invoking procedure.
  - `FINDINGS:`: your teammate's findings. Find each quote by searching for it. A finding whose two quotes stand verbatim in their sources is admitted; for an omission, verify the quoted requirement and the complete inspected file or section instead of demanding nonexistent text: fix it exactly to its REQUIRED OUTCOME and no further; do not reject it, argue with it or put it to the user. Reject a finding only when a quote is not verbatim, the allegedly missing content is present in the cited object, or a NOT AGREED element is covered by a verbatim quote of the agreement, and give that reason with the quote. Fix all admitted findings in one batch, then launch a fresh reviewer with the same level, object and criterion and every rejection so far in `<rejected_earlier>`, until CLEAN.
  - `UNCHECKED:`, missing required `CHECKED:` evidence, a bare `CLEAN`, or malformed evidence: the check is incomplete regardless of its leading verdict. Send the SAME reviewer a short request with `send_input` to supply concise concrete evidence from its retained inspection or mark the exact unavailable requirement `UNCHECKED:`; if the agent is closed, reopen it with `resume_agent` first. Do not start a fresh reviewer merely for format or evidence completion, and never record an incomplete result as acceptance.
  - No verdict, a provider error or a reviewer that could not start: the check has not passed, and no self-check replaces it. Retry the unchanged failed review once under this bounded failure rule; if it fails again, tell the user and wait. A fresh reviewer is otherwise for a changed object or admitted findings requiring a new pass, never for confidence.
