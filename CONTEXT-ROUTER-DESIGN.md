# Context Router: концепция и история решений

Документ хранит причины устройства плагина и историю выбора решений.
В записи от 2026-09-15 переименование и настройка TokenBudget согласованы
владельцем как направление работы. Их реализация закреплена в пакете
`plugins/context-router`; точная конфигурация установщика находится в INSTALL.md.
Предыдущая редакция сохранена ниже как история Context Management.

## Назначение и границы

Context Router сохраняет состояние работы локально и помогает агенту продолжить
её в новом окне Codex. Пакет содержит `memory.js`, skill `local-context-memory`
и hooks. Окна переключает штатный TokenBudget Codex.

Experimental Context Management Codex не участвует в этом решении. Установка
не включает его, не добавляет и не меняет его настройки или модельное поле
`supports_experimental_context`. Настройки, секреты и свойства моделей вне
явно описанного изменения сохраняются.

Целевой пакет — `plugins/context-router`, имя плагина — `context-router`.
Прежний локальный плагин `context-management` заменяется новым штатной
установкой. Прежний путь данных `ctx-mgr-local-native` сохраняется: новая
установка должна продолжить существующие SQLite-базу, настройки и историю.
Кэш установленного пакета не является хранилищем этих данных.

## 2026-09-15: проблема перехода и новое имя

Владелец сообщил о неожиданном обычном compaction при включённом локальном
плагине. После обсуждения он выбрал имя Context Router, чтобы отделить наш
плагин от одноимённой экспериментальной функции Codex, и запретил менять
настройки этой экспериментальной функции. Поэтому решение опирается на
отдельный TokenBudget и существующий локальный CLI.

В текущем чате событие `2026-09-15T00:19:12.615Z` содержит
`compaction_response_id` и элемент `type: compaction` в replacement history.
Это свидетельство серверного сжатия. Пустое поле `message` и надпись
`ContextCompaction` сами по себе не различают способы перехода.

После события наш hook выполнил bootstrap, но вернул `checkpoint: null`.
Следовательно, загрузка плагина и сохранение полезного checkpoint — разные
части результата. Сам плагин не перехватывал смену окна и не вызывал
`new_context` вместо агента.

Прежний INSTALL задавал полную таблицу `[features.token_budget]`: пороги
6000/12000 и инструкции «локальный CLI → checkpoint → native new_context».
Текущий `config.toml` содержит общий флаг TokenBudget, а каталог — модельные
шаблоны для native `notes`/`history`. Полный порядок настройки был утрачен.
В текущем наборе инструментов этого чата `new_context` и
`get_context_remaining` отсутствуют. По сохранённым записям нельзя доказать
время загрузки флага в эту уже существующую сессию.

## Штатный механизм Codex

Исходник OpenAI на ревизии
`653e5fbb9d648a8b99cda14dc164290d6bf34007` устанавливает следующие правила:

- `Feature::TokenBudget` добавляет `new_context` и `get_context_remaining`.
  Experimental Context Management для этой регистрации не требуется.
- Простой boolean включает feature, но не задаёт собственные тексты и пороги.
  Явные поля таблицы бюджета позволяют сохранить пользовательскую конфигурацию
  вместо модельных defaults. Одних `enabled` и `use_history_notes_extension`
  для выбора собственных шаблонов недостаточно.
- При активном TokenBudget ветка автоматического перехода создаёт чистое
  окно без модельной или серверной суммаризации. Она использует общий
  lifecycle compaction, поэтому название события в UI может остаться прежним.
- После перехода выполняются SessionStart hooks. Наш обработчик `compact`
  вызывает обычный bootstrap. Если bootstrap не был передан, skill вызывает
  его один раз через локальный CLI.
- При исчерпании жёсткого лимита Codex может открыть новое окно до очередного
  сохранения агентом. Наличие feature не доказывает наличие свежего checkpoint.

Это чтение исходников, а не результат запуска установленного
`codex-cli 0.154.0-alpha.6.2`. Совпадение двух ревизий не установлено.
Установка не должна выдавать неподдерживаемую возможность хоста за готовую.

## Единственная настройка бюджета

Плагин включается своим штатным механизмом. Независимая настройка бюджета
задаётся в пользовательском `config.toml` одной таблицей
`[features.token_budget]`. Прежний scalar этого же ключа заменяется таблицей;
дублирующий ключ не оставляется. Другие features не переписываются.

| Поле | Значение |
| --- | --- |
| `enabled` | `true` |
| `use_history_notes_extension` | `false` |
| `reminder_threshold_tokens` | `6000` |
| `auto_compact_fallback_buffer_tokens` | `12000` |
| `guidance_message` | Работа через установленный Context Router и его CLI; восстановление при начале окна; точный владелец checkpoint. |
| `reminder_message_template` | `{n_remaining}`; закончить текущий безопасный шаг, сохранить checkpoint, дождаться успеха, вызвать `new_context` перед продолжением. |
| `auto_compact_fallback_prompt` | Прекратить дальнейшую работу, сохранить краткий checkpoint существующим путём исполнения и после подтверждения вызвать `new_context`. |

Это прежние применявшиеся значения, без заявления об измеренном оптимуме.
В текстах нет требования использовать native `notes`, `history`, MCP или
полное суммирование старого разговора. Нет абсолютных путей чужой машины или
версии кэша: актуальные пути CLI и настроек берутся из bootstrap либо из
установленного skill. Если задача уже завершена, агент завершает её обычным
образом и не создаёт новое окно ради самого перехода.

Модельный каталог сохраняет собственные лимиты, effort, возможности и
TokenBudget defaults. Для этой схемы не требуется менять его
`token_budget.enabled` или копировать новые свойства модели: явная полная
таблица является выбранным источником настройки. Переключение модели не
должно возвращать старые native-notes шаблоны.

## Работа агента

В начале работы и после смены окна агент использует переданный bootstrap.
При его отсутствии вызывает `context.bootstrap` один раз. Он читает текущий
checkpoint и только необходимые точные записи истории.

Checkpoint обновляется после значимого результата, принятого изменения
поручения или изменения следующего шага. Мелкие действия объединяются.
Запись после каждого вызова инструмента не требуется. Перед переходом окна
checkpoint должен содержать текущую цель, действующие уточнения, результат,
незавершённое действие, следующий шаг и ссылки на нужные оригиналы.

Детали завершённого этапа сохраняются отдельно только когда они нужны для
продолжения. Если выбран Task Notebook, он остаётся единственным рабочим
планом; checkpoint хранит его точный путь и краткое состояние продолжения.
Параллельный план в SQLite не создаётся.

Владелец записи определяется `thread_id` из bootstrap. Если запись поручена
исполнителю, ему передаются этот ID, точный текст и операция. Нельзя писать
checkpoint основного агента под ID исполнителя из его окружения. Каждый
субагент сохраняет собственное состояние, не меняя общий Goal или чужой план.

На reminder агент не начинает большой новый этап. Через существующий путь
исполнения он сохраняет checkpoint, получает успешный результат и вызывает
штатный `new_context`. `get_context_remaining` используется при необходимости
оценить ближайший большой шаг, а не после каждого действия.

Реальная ошибка записи или чтения сообщается пользователю либо родительскому
агенту. Неизвестный результат записи не объявляется успехом. Автоматическая
подмена этого сценария старым полным summary не предписывается. При forced
reset можно восстановить только фактически сохранённое состояние и доступную
историю; плагин не обещает сохранение данных, запись которых завершилась ошибкой.

## Хранение и hooks

SQLite и настройки остаются в прежней пользовательской папке вне пакета.
CLI не требует MCP или сервиса. Его операции и формат истории сохраняются.
Существующий импорт уже учитывает `compacted.window_id`,
`previous_window_id` и `window_number`; второй импортёр не добавляется.

`SessionStart` и `SubagentStart` восстанавливают контекст при соответствующих
событиях хоста. У прочитанной версии Codex reset/resume дочернего агента не
вызывает start hooks; в отсутствие injected bootstrap skill использует один
`context.bootstrap`. Межагентные PreToolUse/PostToolUse сохраняют исходные записи.
Дополнительный watcher, таймер, router-процесс, флаг состояния или реестр
агентов не нужны.

## Внешние контракты

Context Router использует действующие границы задачи, выбранные workflow и
назначенного исполнителя. Он не владеет Goal, рабочим планом или правилами
делегирования. Locator выбранного Task Notebook берётся из актуального
bootstrap или checkpoint; место хранения определяет Scope Focus.

Budget reminder не разрешает дополнительную работу, не включает Goal или
Task Notebook и не отменяет запрет проверочных запусков. Он использует
действующий путь записи, включая настроенного исполнителя Lunatron.
Помощник не принимает решения за владельца задачи и не переписывает общий план.
Смена окна не завершает Goal и не отменяет новые уточнения пользователя.

## Причины границы между поставкой и работой

Владелец потребовал держать установку и её проверку в INSTALL.md, поскольку
это поручение устанавливающему агенту. Runtime skill адресован агенту,
выполняющему задачу. Custom catalog и общие instructions остаются отдельными
компонентами; их подключение не является скрытым побочным действием skill.

Новый plugin ID не означает новое хранилище: сохранение существующей базы
позволяет продолжить прежние задачи. Настройки хоста читаются при создании
сессии, поэтому перезапуск интерфейса не доказывает появления новых tools
в старом чате. Это ограничение установки, а не причина терять старую историю.

## 2026-09-15: изменения в пакете

Пакет и его hook переименованы в Context Router, источники marketplace и
текущие ссылки согласованы с новым именем. Путь существующих данных сохранён.
Runtime skill закрепляет правильный thread при делегированной записи,
восстановление поправок пользователя, экономные checkpoints и один рабочий
план при выбранном Task Notebook. INSTALL.md содержит явную таблицу бюджета
с локальными инструкциями и штатный порядок замены прежнего пакета.

Эти изменения получены без пробных запусков. Описание native маршрута выше
опирается на чтение исходников; оно не является отчётом о проведённом переходе
в новом чате установленного CLI.

#### 0. Реализация после upgrade

##### Состав и рабочий цикл

Авторитетные исходники находятся в [папке плагина](plugins/context-management/):
[memory.js](plugins/context-management/memory.js),
[skill](plugins/context-management/skills/local-context-memory/SKILL.md),
[регистрация hooks](plugins/context-management/hooks/hooks.json),
[обработчики hooks](plugins/context-management/hooks/context-management.cjs),
[INSTALL.md](plugins/context-management/INSTALL.md) и
[manifest](plugins/context-management/.codex-plugin/plugin.json).
Это один локальный Node.js CLI с SQLite, без MCP и отдельного сервиса.
Базовая версия — `0.0.0`; актуальная сборка указана в manifest.
Требуется Node.js 24.5 или новее.
Пакет рассчитан на macOS, Linux и Windows с Git Bash. Одна пользовательская
папка содержит базу и настройки; секреты и runtime-настройки не переносились.

Плагин устанавливается целиком и не зависит от репозитория разработки.
Отдельных профилей агентов у него нет. Его включение и штатные возможности
Codex — TokenBudget и переход в новое окно — настраиваются отдельно.
Одноимённый native feature flag не является переключателем нашего плагина.
Плагин сохраняет и восстанавливает контекст через свои hooks и `memory.js`;
он не включает функции Codex и не заменяет их.

INSTALL.md всех трёх плагинов имеет общий порядок: состав, требования,
первая установка, проверка после установки и обновление. Доверие к конкретным
hook-определениям устанавливается через штатный Codex app-server без обхода
trust. Проверку из INSTALL выполняет устанавливающий агент в конце установки
на целевой ОС; в Windows — через Git Bash. Эти требования к установке не
означают, что такие запуски были выполнены при редактировании дизайна.

Смена окна остаётся механизмом Codex. Skill требует по сигналу TokenBudget
сохранить `/root/notes/stages/<stage>.md`, затем
`/root/notes/checkpoint.md` с целью, ограничениями, результатами, следующим
действием и ссылками на этапы и `window_id/item_id`. После успешной записи
агент использует штатный переход в новое окно. CLI сам не считает бюджет,
не создаёт смысловые summary и не запускает переход: это действия агента
по инструкции. Отдельной таблицы этапов нет — этапы являются обычными notes.

В новом окне используется bootstrap, уже переданный hook. Если его нет,
skill требует один обычный `context.bootstrap`, в том числе после reset/resume
ребёнка, где начальный hook не повторился. Bootstrap возвращает текст
checkpoint, revision, пути CLI/skill/settings, результат импорта или
`history_error` и до пяти последних непустых записей с ролью `user`.
Повторное чтение уже полученного checkpoint и отдельная проверка source status
не требуются. Исходники по ссылкам читаются только для продолжения задачи.

##### Хранилище, импорт и точное чтение

| Часть | Что делает текущий код |
|---|---|
| Миграция | `openDb` в одной транзакции переносит старую `import_sources` в схему с `(visible_thread, source_key)`, добавляет ключи источников и признаки происхождения. `notes`, revisions, `write_receipts`, старые canonical/window id не переписываются. Привязка legacy rows использует сохранённые тред и путь. |
| Поиск сегментов | `sourceCandidates` собирает JSONL с id треда в имени из `sessions` и `archived_sessions`. Кандидаты сортируются по timestamp заголовка, при его отсутствии — по пути. Импорт проверяет id сессии и `context_window.window_id` в `session_meta`. |
| Идентичность | В пределах видимого треда новому источнику выдаётся сохранённый UUID `source_key`. Совпавшие dev/inode позволяют сохранить ключ при переносе; у каждого источника свой cursor. Новые native id включают исходный тред, ключ сегмента и byte offset. Native ordinal хранится отдельно от порядка вставки. |
| Записи | Каждая новая полная JSONL-строка, включая служебный и неизвестный тип, сохраняется в `raw` без завершающего LF/CRLF. Из известных полей отдельно извлекаются текст и метаданные. Проверки списка версий и равенства native ordinal физическому номеру строки удалены. |
| Происхождение | `native_full_record` означает полную сохранённую строку, `legacy_payload` — ранее сохранённый payload, `harness_record` — оригинал, переданный Harness. Сохранённый ciphertext не становится plaintext; распознанные случаи без извлечённого текста имеют `unavailable_original=1`. |
| Наследование | `history_base` использует `end_byte_offset` и `end_ordinal_exclusive`. Выбираются упорядоченные родительские сегменты до сегмента с подтверждённой границей. Проверяется завершитель строки; ordinal проверяется, когда передан `end_ordinal_exclusive`. Неоднозначная граница возвращает ошибку. |
| Частичный импорт | Обычный вызов ограничен 4 MiB/256 записями. Для одной длинной строки чтение может расширяться до лимита строки 16 MiB. Незавершённый хвост не импортируется. Источники возвращают cursor, boundary и `catching_up`; `ready` относится к выбранному набору файлов и текущим границам. |
| Замена источника | Для завершённого источника при обнаруженной замене старое поколение помечается `superseded` и исключается из обычных списков, поиска и user refs. Известный старый `item_id` остаётся доступным напрямую. Замена незавершённого источника возвращает `source_replaced`. |
| Чтение | `history.read_item` сначала ищет точный id в базе; найденная запись не требует доступного JSONL. При промахе выполняется обычный импорт. `format=text\|raw` использует SQL `substr`, `offset_chars/limit_chars` и `next_offset_chars`; большие `raw/text` целиком в ответ не вкладываются. |
| CLI и повторы | Сохранены `notes.*`, списки/поиск истории и bootstrap; добавлен `history.record`. Он использует стабильный id и обычный `request_id` receipt. Receipt сравнивает тред, операцию и вложенные args. Поддерживаются формы flags с дефисом/underscore и `=`, лимит всего JSON-ответа — не более 64 KiB. |

Успешная запись checkpoint может содержать `saved: true` вместе с
`history_error`: notes сохранены, импорт не удался. Это разные результаты
одной обычной операции. Запись в базе не доказывает чтение агентом и не
является подтверждением доставки сообщения другому агенту.

##### Hooks и субагенты

`hooks.json` регистрирует `SessionStart` для startup/resume/clear/compact и
`SubagentStart` для начального запуска ребёнка. Оба обработчика вызывают
тот же `context.bootstrap` и возвращают `additionalContext`. Identity берётся
из `agent_id`, затем `session_id`; при отсутствии id возвращается сообщение
об ошибке, общий тред `/root` больше не подставляется.

`PreToolUse` и `PostToolUse` зарегистрированы для `spawn_agent`, `send_message`,
`followup_task`, `send_message_to_thread`. До вызова в треде отправителя
сохраняется вход. После вызова сохраняются результат и, если удалось получить
адресата, отдельная transfer-запись в его треде. Для spawn адресат берётся из
прямых полей результата; предполагаемый путь ребёнка не используется для
transfer. Записи связываются через `tool_use_id`. Без него pre и post получают
независимые хеши своих payload и общей связи не образуют. Transfer содержит
`parent_thread`, `tool_input` и `tool_response`; дополнительные ссылки
передаются в `refs`.

Вызовы CLI в hooks синхронные, с timeout 6 секунд на вызов. В регистрации
задан timeout 7 секунд на обработчик. Hooks не возвращают запрет инструмента
и не содержат guard, очередь, retry, delivery receipt или health probe.
При полученной ошибке обработчик формирует `additionalContext` с просьбой
сообщить её: ребёнок — родителю, основной агент — пользователю. Ошибка процесса
hook, скрытая самим Codex, не гарантированно попадёт модели.

##### Что осталось ограниченным

Этот раздел отличает фактическую реализацию от более сильных обещаний проекта.

- **Обычный compaction:** автоматического переключения с TokenBudget на
  full-summary compaction нет. Skill описывает ручной аварийный путь после
  сообщения об ошибке, если такой путь доступен в текущем Codex.
- **Полнота старых оригиналов:** миграция сохраняет старые payload и cursor.
  Она не перечитывает автоматически весь уже пройденный участок и не
  восстанавливает отсутствующий JSONL, ciphertext или обрезанный вывод.
  `unavailable_original` распознаёт конкретные поля `encrypted_content` и
  `ciphertext` при пустом извлечённом тексте, а не все возможные закрытые форматы.
- **Границы и порядок:** поиск зависит от имён файлов; порядок уже вставленных
  записей не пересчитывается при позднем обнаружении более раннего сегмента.
  Рекурсивный вызов импорта `history_base` возвращает состояние, которое
  вызывающий `importSegment` отдельно не объединяет со своим статусом.
  Поэтому `ready` нельзя считать общим доказательством полноты всей цепочки.
- **Продолжение длинного checkpoint:** `fitResult` может вернуть его часть с
  `next_offset_chars`, но `notes.read_file` принимает границы строк, а не этот
  символьный cursor. Единый автоматический путь продолжения ещё не реализован.
- **Ссылки между агентами:** `refs` сохраняются в колонке `attachments`, но
  `history.read_item` сейчас её не возвращает. Transfer raw содержит само
  задание и результат; выдача всех служебных связей через reader не закончена.
  При отсутствии общего `tool_use_id` хеши input/output также не гарантируют
  одну связь. Копирование transfer после ответа не гарантирует его наличие
  до первого модельного шага ребёнка.
- **Доставка hooks:** код рассчитывает на перечисленные события, имена tools
  и прямые поля ответа. Другие внутренние каналы V1/V2 не перехватываются
  автоматически. Несколько последовательных CLI-вызовов в одном PostToolUse
  могут суммарно превысить timeout обработчика. Нельзя объявлять сообщения об
  ошибке и восстановление любого ребёнка безусловно гарантированными.
- **Разделение user/service:** все исходные строки сохранены, но bootstrap
  выбирает `role='user'` и непустой текст. Прежний фильтр `content_item_kinds`
  не сохранён; user refs не являются гарантированным списком только просьб
  владельца. Синхронизация баз между хостами отсутствует.

##### Статус прежних исправлений и проверок

| Предмет прежнего разбора | Состояние в upgrade |
|---|---|
| P1: один файл, ordinal и whitelist версии | Заменены поиском сегментов, отдельными ключами/cursor и чтением полных строк. Полная совместимость со всеми форматами этим не доказана. |
| P2: исходники V2 | Добавлены Harness-записи и transfer через hooks. Старые зашифрованные сообщения не расшифровываются; ограничения доставки перечислены выше. |
| P3: checkpoint без истории | Bootstrap включает текст и `history_error`; reader работает с cached id. Skill требует сообщать реально полученную ошибку, без отдельных проверок. |
| P4: поиск/возврат данных | Reader получает страницу через SQL; списки/поиск имеют лимиты ответа. Полной переделки всех note readers в потоковые операции нет. |
| Очистка `memory.js` | Удалены `MemoryError.status`, whitelist версий, single-source importer, отдельный writer `memory.events.jsonl`, безусловный импорт перед cached read и дубли CLI parsing. Существующие базы, настройки и старые журналы не удалялись. |

В ходе реализации зафиксированы успешные `node --check` для `memory.js` и
обработчика hooks и один временный CLI-сценарий: `history.record`, чтение
Unicode raw `{"message":"Привет 😀"}` через `item_id`, завершение страницы
с `next_offset_chars=null` и повтор той же записи с тем же `request_id`.

Это подтверждение данного CLI-сценария и синтаксиса. Runtime-проверка миграции
реальной старой базы, native-импорта, полной смены окна и цикла parent/child
в V1/V2 не выполнялась. Прежний итоговый `CLEAN` был результатом статического
review, а не таких запусков. При этой сверке документа новых запусков нет.
Код сохраняет ограничения выше; формулировка «полностью стабильно работает
во всех режимах» не подтверждена имеющимся результатом.

#### 1. Исходная задача и восстановление до upgrade

После смены окна агент должен продолжить действующую задачу: сохранить цель,
ограничения, принятые решения, результаты и следующий шаг. Если сведения
в checkpoint недостаточны, он должен получить точный исходный запрос,
сообщение, вызов инструмента или доступный результат из прежней истории.
Новое указание владельца имеет приоритет над отменённой старой задачей.

В этой схеме пять разных вещей:

| Слой | Назначение |
|---|---|
| Активное окно модели | Содержит только текущий доступный модели контекст. |
| Checkpoint / notes | Хранит полное текущее состояние задачи, решения, результаты и ссылки. Это текст, составленный агентом. |
| Rollout JSONL | Хранит доступные исходные записи разговора, инструменты и границы истории. |
| History API / CLI | Находит нужные записи и возвращает их по устойчивым ссылкам. |
| Восстановление | Агент читает checkpoint и нужные первичные записи, а затем использует их в работе. |

Успешная запись notes не доказывает доступность JSONL. Доступность JSONL
не доказывает полноту импорта. Наличие `history.read_item` не доказывает,
что агент вызвал его и получил нужное сообщение. Именно эти различия
оказались важны при разборе неисправностей.

Skill до upgrade требовал после сброса вызвать `context.bootstrap`, проверить
задачу и состояние источника, прочитать checkpoint, затем каждый выданный
`user_refs` через `history.read_item`. При отсутствии ссылок предусмотрены
список окон, список записей или поиск. См.
[инструкцию восстановления до upgrade](https://github.com/ARQAWA/my-codex-harness/blob/4e3c57a63f14d9117a4c6a1ef89beda5a789da5e/plugins/context-management/skills/local-context-memory/SKILL.md#L39).

#### 2. Все основные варианты реализации из обсуждений

##### A. Штатный экспериментальный `context_management`

Первоначальная концепция опиралась на штатные TokenBudget, `new_context`,
history и notes в Codex. Модель освобождает активное окно и восстанавливает
состояние через заметки и историю. Это отличается от обычного compaction,
который продолжает разговор на основании сжатого представления истории.

В ранних исследованиях notes/history относили к backend Codex, а локальный
`rollout-*.jsonl` — к отдельному источнику полных доступных записей. Вызовы
notes/history реально возвращали `backend request failed`, в том числе 404.
Это стало причиной поиска локальной реализации. Локальный плагин не исправил
сам закрытый backend OpenAI. Доступность экспериментальной серверной функции
нельзя выводить только из наличия флага или инструментов. Источники: S5–S9, S13.

##### B. HTTP proxy и перехват запросов

В прежнем варианте использовался proxy-путь. Поздний локальный дизайн отказался
от зависимости от перехвата запросов: историю предложили брать из JSONL,
а память обслуживать отдельно. В прежнем `ctx-mgr-local` сохранился `proxy.js`,
но наличие старого файла не делает этот вариант текущей архитектурой.

Для последующего локального решения были зафиксированы ограничения: без fork
Codex, подмены provider URL, моделей и namespace инструментов. Возвращение
proxy — отдельный архитектурный выбор, а не уже выполненный фикс. Источники:
S2–S4 и `local-context-mechanism-design.html`.

##### C. Постоянный backend + лёгкий CLI + skill + MCP-мост

Промежуточный выбранный дизайн: локальный daemon обслуживает SQLite,
CLI выполняет обращения к нему, skill описывает поведение агента.
Небольшой штатный MCP-мост `notes.thread_hint` передаёт указатель для начала
нового окна. MCP здесь нужен для автоматического входа в восстановление;
он не должен подменять собой всю историю.

JSONL дочитывается по запросам, а не через постоянное сканирование всех чатов.
Плюс варианта — исследованный путь доставки подсказки после сброса.
Цена — отдельный процесс, подключение клиента, настройка путей и живой MCP.
Остановленный backend или неверные пути делают память недоступной.
Этот вариант был заменён одноразовым CLI. Источники: S1–S4,
`local-context-mechanism-design.html`, разделы 1–5 и 12.

##### D. Одноразовый CLI + SQLite + skill, без собственного сервера и MCP

Позднее владелец выбрал схему: один вызов открывает существующую SQLite,
выполняет ограниченную работу, возвращает результат и завершается.
Постоянными остаются файлы базы, настроек и журнала. Отдельный daemon,
HTTP-сервер, proxy и фоновый наблюдатель для этой схемы не нужны.

Восстановление должно начинаться через штатную guidance Codex: она указывает
на skill, CLI и настройки. Идентификатор задачи берётся из `CODEX_THREAD_ID`.
Переключением окон и учётом токенов продолжает управлять сам Codex.

В переходном документе установка нового CLI и отключение старого MCP ещё
были отложены. Там же было явно сказано: основания для guidance получены
из исходников 0.153.4 и фактически доставленной инструкции; полный запуск
установленной 0.154.0-alpha.6.2 без MCP в той задаче не проводился.
Позднее в S1 агент сообщил об установке и отключении прежнего сервера/MCP.
Текущий `memory.js` реализует одноразовую схему. Эти стадии нельзя смешивать.

Условия автоматического восстановления: активный TokenBudget, известный
размер окна модели и корректная guidance. Разовая инструкция пользователя
не доказывает доставку указателя после каждого будущего сброса. Источники:
S1, `memory-without-mcp-design.html`, разделы 1–2 и 5–7.

##### E. Упаковка в самостоятельный плагин и перенос в harness

CLI и skill были упакованы в Context Management и перенесены в
`plugins/context-management`. В пакете должны находиться код и skill;
отдельная пользовательская папка содержит базу, журнал и настройки.
Сохранённые пути старой установки не должны подменять CLI/skill нового пакета.
Текущий `readSettings` исключает переопределение `cli_path` и `skill_path`
из сохранённых settings.

Для установки отдельно нужны подходящий Node.js, настройка Codex и связь
guidance с установленным skill. Одна регистрация плагина этого не доказывает.
Уже открытые задачи могут сохранять старые инструкции. Перенос ZIP не переносит
историю между машинами: SQLite локальна для каждого хоста. Установка на чистом
другом хосте в финальном отчёте S1 прямо названа непроверенной.

В текущем репозитории установка отделена от разработки. Root-документ дизайна
не должен становиться зависимостью установленного пакета. Источники: S1, S10,
[INSTALL.md](plugins/context-management/INSTALL.md),
[манифест](plugins/context-management/.codex-plugin/plugin.json).

##### F. Обычное сжатие истории

Обычный compaction сохранялся как штатный путь Codex. В раннем исследовании
одной сессии были найдены 12 `contextCompaction` и ни одного `new_context`.
Это наблюдение не означает, что экспериментальный механизм работал во всех
остальных сессиях или что каждый backend-вызов виден в rollout.

Позже владелец отключил Context Management и в S12 выбрал обычное сжатие.
Для Kimi адаптер формирует совместимое с Codex сжатие средствами выбранной
модели. Это выбранный обходной путь, а не исправление локального импортёра
JSONL. Ошибка адаптера `compaction v2` и пустого сообщения была отдельной
неисправностью; её исправление было заявлено в S12. Короткие успешные запросы
не доказывают поведение на всех длинных сессиях. Источники: S11–S13.

#### 3. Принципы прежних локальных концепций

Ниже сохранены принципы и интерфейсы до upgrade. Новая версия хранит также
служебные исходные строки; её id, фильтры, статусы и лимиты описаны в разделе 0.

##### Источник, идентичность и границы истории

- История берётся из исходных JSONL, а не создаётся пересказом notes.
- `response_item` — первичная запись. Зеркальный `event_msg` нельзя добавлять
  второй копией того же сообщения.
- Начальное окно описывает `session_meta.context_window`, переходы — записи
  `compacted`. Любой hint или обычный текст не является границей окна.
- Метаданные `content_item_kinds` с `user.text` использовались, чтобы отличать
  настоящую просьбу владельца от служебного блока с ролью `user`.
- `history_base` задаёт унаследованный префикс. Нельзя читать всю будущую
  историю родителя только по `forked_from_id`: идентификаторы могут различаться.
  Важны `end_byte_offset` и исключительная граница `end_ordinal_exclusive`.
- Canonical ID сохраняет связь с источником и ordinal; исходный ID хранится
  как alias. Для поддержанного случая без ordinal предусмотрена ссылка
  через byte offset. Сокращать canonical ID при повторном чтении нельзя.
- `raw`, извлекаемый текст, вложения и признак усечения — разные данные.
  Скрытый reasoning, закрытые аргументы и зашифрованные payload нельзя объявлять
  восстановленными только потому, что сохранён их opaque-контейнер.

Эти принципы полезны, но реализация идентичности и ordinal оказалась уже
реального формата. Ошибки перечислены в следующем разделе.

##### Импорт и состояние источника

Проект предусматривал курсор: источник, его идентичность, byte offset
и ordinal. Импортированные записи и новый курсор фиксируются одной
транзакцией. Неполная последняя строка остаётся до следующего обращения.
Повторный запрос не должен дублировать уже импортированную запись.

| Состояние | Допустимый смысл |
|---|---|
| `ready` | Доступная и заявленная граница источника дочитана. Сам по себе статус не доказывает, что обнаружены все файлы истории задачи. |
| `catching_up` | Импорт ограничен объёмом одного вызова; следующие обращения продолжают его. |
| `partial` | Доступна только часть источника или неполный хвост. |
| `source_not_ready` / `not_ready` | Источник пока недоступен или не готов. |
| `source_incompatible` | Формат или проверка источника не приняты импортёром. Это ошибка, а не пустая история. |

Запись checkpoint сознательно разрешили независимо от полного завершения
импорта. `revision` подтверждает запись notes; она не подтверждает полноту
history. Bootstrap может вернуть checkpoint вместе с `history_error`.
Skill должен учитывать это различие. См.
[bootstrap до upgrade](https://github.com/ARQAWA/my-codex-harness/blob/4e3c57a63f14d9117a4c6a1ef89beda5a789da5e/plugins/context-management/memory.js#L754).

##### Транзакции, повтор запросов и параллельная работа

В одноразовой схеме выбран один механизм взаимного исключения — SQLite.
Проект описывает `BEGIN IMMEDIATE` перед изменяемым состоянием и курсором,
операцию и receipt внутри транзакции, `SAVEPOINT` для локального отката,
успех после `COMMIT`, закрытие базы при завершении вызова.

`request_id` защищает повтор того же запроса от двойного выполнения.
Для нового намеренного изменения нужен новый запрос. `revision` — номер
результата записи; отдельную новую систему проверки ревизий и разрешения
конфликтов в этот переход не добавляли.

Проектный `busy_timeout` — 5 секунд. Это один активный писатель, а не строгая
очередь FIFO. Несколько процессов не получают обещания обслуживания в порядке
прихода; запрос может завершиться ошибкой занятости. Собственную очередь,
бесконечные повторы и новый диспетчер для этого не проектировали.

##### Ограничения объёма

Ранний код читал большие диапазоны и собирал промежуточные массивы.
Одного ограничения размера итогового JSON для расхода памяти недостаточно.
Поздний вариант перешёл к ограниченной дочитке и выдаче страниц.

| Параметр | Зафиксированное значение |
|---|---|
| Вход CLI | 8 MiB |
| Одна заметка | 1 000 000 байт |
| Ответ | До 64 KiB |
| Блок чтения файла | 64 KiB |
| Одна строка JSONL | До 16 MiB |
| Квота импорта на вызов | До 256 записей или около 4 MiB источника |
| Глубина наследования | До 32 |

Последняя начатая запись может потребовать дочитки сверх квоты вызова,
до предела одной строки. Для цепочки родителей квота общая. Большую строку
нельзя молча пропустить с продвижением курсора. Эти числа — выбранные
ограничения алгоритма, не измеренный RSS и не гарантия жёсткого лимита RAM.
Источники: S1, `memory-without-mcp-design.html`, разделы 3–4,
[константы реализации до upgrade](https://github.com/ARQAWA/my-codex-harness/blob/4e3c57a63f14d9117a4c6a1ef89beda5a789da5e/plugins/context-management/memory.js#L10).

#### 4. Ошибки, подтверждённые до upgrade

##### P1. Один зарегистрированный файл вместо всей доступной истории

`sourceCandidates` выбирает один лексикографически минимальный подходящий
JSONL. После регистрации импорт продолжает использовать `source_file`.
Это не сбор всех продолжений задачи.

В реальном чате S1 есть базовый файл и продолжение:

| Поле | Наблюдавшееся значение |
|---|---|
| Задача | `01a0951e-b1f9-7d72-9e26-6b3b82d417e2` |
| Начало базового файла | `ordinal=0` |
| Начало файла с суффиксом `_01a09531-0aa0-72f3-ab5e-4d3007c78b77.jsonl` | `ordinal=422` |
| `session_meta.id` продолжения | Тот же ID задачи |
| `history_base` продолжения | Та же задача; `end_ordinal_exclusive=422`, `end_byte_offset=1220860` |
| Текущее наблюдение в `import_sources` | `ready`, курсор `ordinal=431`, зарегистрирован только базовый файл |

Поздние сообщения в продолжении не становились частью истории, импортируемой
из единственного базового файла. При этом статус `ready` оставался возможным.
Суффикс имени файла нельзя без проверки метаданных считать отдельной
независимой задачей и на этом основании исключать его из разбора.

Источники: [выбор файла до upgrade](https://github.com/ARQAWA/my-codex-harness/blob/4e3c57a63f14d9117a4c6a1ef89beda5a789da5e/plugins/context-management/memory.js#L237),
S1 и существующая локальная `memory.sqlite3`, таблица `import_sources`.

##### P2. Неверное предположение о нулевом и физическом ordinal

Импортёр требует нулевой ordinal у первого `session_meta`. Далее он сравнивает
ordinal записи с числом прочитанных строк выбранного файла. Реальное
продолжение S1 начинается с 422; другое исследованное продолжение S4 — с 2301.
Их ordinal продолжает логическую историю, а не начинается заново с нуля.

Поэтому простого выбора другого имени файла недостаточно: действующая
проверка отвергает такой заголовок. Кроме того, ветка наследования пропускает
`history_base`, когда его thread ID совпадает с текущим, хотя именно такой
заголовок наблюдается в S1. Эти условия нужно рассматривать вместе с P1,
а не исправлять только сортировку имён.

Источники: [проверка записей до upgrade](https://github.com/ARQAWA/my-codex-harness/blob/4e3c57a63f14d9117a4c6a1ef89beda5a789da5e/plugins/context-management/memory.js#L464),
[проверка заголовка до upgrade](https://github.com/ARQAWA/my-codex-harness/blob/4e3c57a63f14d9117a4c6a1ef89beda5a789da5e/plugins/context-management/memory.js#L513),
ветка наследования в `importHistory`, заголовки реальных продолжений S1/S4.

##### P3. `realtime_item` останавливает чтение истории

В `import_sources` для S10 сохранено:
`source_incompatible`, `unsupported rollout record type: realtime_item`.
Курсор остановлен на ordinal 842. Такой тип отсутствует в разрешённом списке
`parseRecord`. Перед каждой history-операцией вызывается `ensureHistory`,
поэтому ошибка дочитки блокирует и запросы к истории.

В существующем `memory.events.jsonl` наблюдается последовательность:

1. `context.bootstrap` — `ok`;
2. `notes.read_file` — `ok`;
3. `history.list_windows` — `error`, `source_incompatible`;
4. `notes.write_file` — `ok`.

Она повторяется; характерные строки журнала — 421–425 и 437–439.
Это прямое подтверждение симптома «checkpoint работает, история недоступна».
Речь не о запрете доступа ко всем JSONL: в S12 есть и успешные
`history.list_windows`, `history.list_items`, `history.read_item`.

Источники: [разрешённые типы до upgrade](https://github.com/ARQAWA/my-codex-harness/blob/4e3c57a63f14d9117a4c6a1ef89beda5a789da5e/plugins/context-management/memory.js#L464),
S10, существующие SQLite и журнал локальной памяти.

##### P4. Неверное основание для заявления о готовности

В продолжении S1 было написано: «Новая механика уже работает:
`context.bootstrap` вернул `ready`». Это сообщение находится в строке 1038,
ordinal 1459, файла продолжения, указанного в P1.

Но `ready` для одного обнаруженного файла не доказывал охват продолжений.
Успех bootstrap и notes также не доказывал успешное чтение истории, что видно
по P3. Ошибка приёмки состояла в слишком широком выводе из узкого результата.
Это не утверждение, что ранее вообще не было тестов: были разные проверки
и отчёты, но они не исключили обнаруженные рабочие отказы.

#### 6. Варианты исправлений, обсуждавшиеся до upgrade

Этот раздел сохраняет предложения первоначального разбора 14 сентября.
На тот момент они **не были внедрены и выбраны владельцем**. После этого запрос
на upgrade изменил статус части предложений; фактический результат и остаток
указаны в разделе 0. Перечень ниже сохраняется как история найденных проблем
и альтернатив, а не как новый заказ на реализацию.

##### История и её продолжения: P1/P2

**Полное исправление существующего локального пути:** учитывать связанные
файлы/продолжения по метаданным и границам источника, а не принимать один
минимальный путь за всю задачу. Разделить идентификатор задачи, конкретный
источник и его базовый ordinal. Не требовать, чтобы каждый реальный сегмент
начинал нумерацию с нуля. Сохранять унаследованный префикс, даже когда
`history_base.thread_id` совпадает с ID текущей задачи, если это соответствует
реальным данным. Не импортировать будущие записи вне разрешённой границы.

**Ограниченный безопасный вариант:** явно признать неподдержанные продолжения
и не объявлять всю историю готовой. Это устраняет ложный успех, но не решает
задачу восстановления старых ходов. Выбранным тогда обходом было обычное сжатие.

**Чего недостаточно:** поменять сортировку на «самый свежий файл», убрать одну
проверку ordinal или склеить все совпавшие имена. Такие действия сами по себе
не устанавливают принадлежность, порядок и границы истории.

##### Новые типы записей: P3

**Поддержать реальный формат:** определить роль `realtime_item` в поддержанных
версиях и корректно сохранить либо обработать его. Для известных служебных
записей, не меняющих историю сообщений или её границы, возможно явное правило
пропуска при импорте items. Это требует понимания типа; оно не означает
«игнорировать всё неизвестное».

**Сохранить строгий отказ для неизвестной семантики:** если тип может менять
историю или её границы, возвращать несовместимость с точным источником.
При этом bootstrap/восстановление должны ясно сообщать недоступность history.
Молчаливое продолжение только по checkpoint не является полным исправлением.

**Отдельный ограниченный вариант:** позволять чтение уже подтверждённой части
истории при ошибке последующей дочитки, сохраняя явную границу и ошибку.
Он может вернуть доступ к старым items, но не гарантирует полноту и требует
отдельного решения; в текущем пути `ensureHistory` это не обеспечено.

##### Готовность и восстановление: P4

Разделить успех записи checkpoint, состояние импорта и успешное чтение нужных
первичных записей. Заявление «память работает после сброса» должно относиться
ко всей этой цепочке. `revision`, ответ bootstrap и пять последних `user_refs`
по отдельности этого не доказывают.

Существующие `user_refs` ограничены пятью последними пользовательскими
сообщениями. Это полезный вход в историю, но не полный действующий запрос.
Старые важные решения должны оставаться достижимыми через checkpoint-ссылки
и поиск. Этот предел не установлен как единственная причина наблюдавшихся
сбоев; для P1–P3 имеются более прямые доказательства.

Варианты доставки указателя уже известны: штатный MCP hint или статическая
guidance. Выбор между ними не исправляет повреждённый импорт. Ни один skill
не даёт жёсткой гарантии, что модель выполнит все шаги или что клиент никогда
не сбросит окно до сохранения. Если в будущем потребуется такая гарантия,
это изменит прежнее ограничение «без изменения Codex» и потребует решения
владельца. Сейчас она не обещана.

ошибка history не подменяется успехом notes. Это основания для будущей
приёмки, а не поручение сейчас запускать тесты или менять плагин.

#### 8. Сохраняющиеся ограничения

- Нельзя объявлять checkpoint полной первичной историей или обещать возврат
  отсутствующих/обрезанных данных.
- Бюджет контекста, TokenBudget, добровольный `new_context` и принудительный
  reset — разные механизмы. Локальная SQLite ими не управляет.
- Рабочие ссылки должны сохранять точную идентичность сообщения и границы
  доступа. Старые отменённые указания не возобновляются поверх новых.
- В новой версии нет whitelist `0.153.4`/`0.154.0-alpha.6.2`. Импорт зависит
  от реально читаемых полей `session_meta`, окна и границ; сохранение неизвестной
  raw-строки не доказывает понимание её смысла или поддержку любого JSONL.
- Не переносить исторические пути установки, состояние MCP или модельные
  ограничения в описание текущего runtime без отдельного основания.
- Локальная база на каждом хосте самостоятельна. Синхронизация, перенос
  истории и восстановление закрытых данных не были реализованы.
- Возврат к native backend, proxy, daemon или изменению Codex — отдельные
  варианты, а не неявные части небольшого исправления импортёра.
