# Установка

## Состав

Пакет содержит два hook-определения: `SessionStart` и `UserPromptSubmit`,
skill с явным поручением делегировать
при активном Lunatron, контракт Main, Node.js CLI для
подготовки контекста, CLI для полного захвата потенциально большого вывода и
профили `agents/lunatik.toml`, `agents/luntik.toml`,
`agents/lunatron_luna_xhigh.toml`, `agents/lunatron_sol_low.toml`,
`agents/lunatron_sol_medium.toml` и `agents/lunatron_sol_xhigh.toml`.
Lunatik (gpt-6-luna/medium) выполняет простую реализацию и механику, постоянный
Luntik (gpt-6-luna/medium) — простой вопрос к выбранным большим данным, Luna XHigh
(gpt-6-luna/xhigh) — сложный блок. Main Luna использует только Luna. Любой Main
вне Luna выбирает также Sol 6.1 Low для регулярной сложной аналитики, когда Luna
недостаточна, Medium для очень сложной и Extra High для исключительной; effort
закреплён профилем, без наследования max или обязательной лестницы проб.
Sol владеет своим блоком, сам пишет и сохраняет аналитику, документы и промпты,
включая embedded prose. Код любой сложности и разрешённые механика/запуски обычно
идут его собственным Luna полным форком текущего контекста: Lunatik для простой,
Luna XHigh для сложной реализации. План содержит достаточные решения словами,
точные cwd/ownership/references/values, действия, порядок и условия результата;
новые готовые code bodies/patches/snippets не передаются для копирования. Luna
сама генерирует код; существующий и пользовательский код остаётся данными. Только
действительно неотделимую реализацию Sol пишет сам с конкретной причиной;
сложность, удобство или нет slot/role не являются причиной. Это не разрешает runs.
Luna возвращает final своему непосредственному Main либо Sol; Sol завершает блок
и сообщает Main. Все агенты доверяют готовым итогам без повторного чтения,
исследований/checks или handoff review. Приёмка не является инспекцией кода.
Конкретный пробел/проблема, новая работа и явно назначенный reviewer имеют свои
границы. Существенный gap возвращается владельцу как DECISION_REQUIRED; обычное
общение — назначение и final, без дублирующего send. Native wait при зависимости
и отсутствии нужной независимой работы исключает polling/повторное рассуждение;
длинный timeout соблюдает предел инструмента, тихий timeout не доказывает сбой.
Все потомки, включая Sol parents, Luna, Luntik и reviewers, делят фактическую
native ёмкость с целевым лимитом 44 без Main; требуемым Luna сохраняется место.
Нет cap15, фиксированных квот, scheduler, max_depth или нового state. Config 44
не доказывает live capacity; active-turn и open-thread caps различны. При отсутствии
обязательного slot/роли/full fork зависимый блок останавливается без подмены.
Непосредственный родитель закрывает one-shot доступной native операцией с
acknowledgment, включая error results. Final/interrupt не доказывают closure или
open-slot release; недоступный close сообщается без обхода, id не переиспользуется.
Child INACTIVE снимает root обязанности, сохраняя узкое Sol→Luna право профиля;
Sol→Sol цепочки и произвольные Luna workers не разрешены. Reviewer выбирается
своим review-skill. Main может поручить любой skill кроме goal в границах блока;
исполнитель читает SKILL.md. Root scope, внешняя authority, native Goal, приёмка
всей задачи и ответ пользователю остаются Main. Skill не расширяет полномочия.

CLI извлекает фрагменты для ответа Main;
он нужен для требуемых точных цитат и структурного чтения сохранённых
результатов и буквальный поиск. Capture CLI запускает переданную программу без
shell, сохраняет полные stdout и stderr раздельно до host-усечения и возвращает
пути, размеры, exit code, signal и полноту.
Выданная хуком `capture_call` передаёт фактический `PLUGIN_DATA` только процессу
CLI с экранированными путями; глобальное окружение менять не нужно.
Полнота захвата не означает успех команды: отдельно учитываются её exit code
и signal. Новые управляющие состояния и интерфейсы CLI не добавляются.

Системный промпт — отдельный компонент поставки, не часть плагина.
После repo-level setup runtime-пакет самодостаточен и не зависит
от документации репозитория.

## Требования

Нужны Codex CLI с поддержкой плагинов, hooks, app-server, native full-context
fork, Node.js и все шесть профилей помощников.
Main выбирает вызовы и параметры по текущим описаниям инструментов.
Каждый помощник возвращает final и завершает ход. Закрытие обязательно, когда
есть поддерживаемый способ; без него работа продолжается. Завершение хода
не означает закрытие; неподтверждённое закрытие не объявляется успешным.
Main раскрывает доступные native-инструменты перед первым нужным форком.
Недоступность обязательной возможности требует сообщения о несовместимости,
без скрытой замены исполнением в Main. Дочерний контекст снимает только обязанности
root-оркестратора; профиль, поручение и его границы продолжают действовать.
В `config.toml` активного Codex home установи штатный предел одновременных
дочерних задач не ниже 44, сохранив более высокое существующее значение:

```toml
[agents]
max_concurrent_threads_per_session = 44
```

Если `[agents]` уже есть, добавь или обнови только этот ключ и сохрани прочие
настройки. Профили Lunatron закрепляют модель и effort; Main выбирает нужный
профиль при запуске, без подмены другой ролью.
Зависимостей npm нет. Поддерживаются macOS, Linux и Windows; в Windows
используется только Git Bash, без PowerShell. Lunatron и Tritron не должны
работать одновременно.

Плагин и оба hooks (`SessionStart`, `UserPromptSubmit`) должны быть включены
после установки и обновления.
Сам режим Lunatron по умолчанию включён для корневой задачи на любой модели.
При `LUNATRON_STATE=ACTIVE` hook прямо указывает Main прочитать bundled skill,
который поручает делегировать подходящие блоки, включая короткие команды без
параллельной работы. Обычный поиск, малые чтения и приёмка остаются у Main;
чистый вопрос не требует помощника. `LNT0` выключает режим: Main останавливает
всё дерево работающих помощников своей задачи, устанавливает состояние прерванных изменений и закрывает
помощников текущей задачи поддерживаемым способом. Отсутствие способа закрытия
не блокирует выключение. Команды слитные, регистр любой, границы —
пробельный символ или начало/конец сообщения. Они распознаются в любом месте
корневого сообщения пользователя, в том числе в блоке кода; последняя команда
побеждает. Остальная просьба в сообщении сохраняется. `LTN`, пробел внутри
команды и `-1` не поддерживаются.
Явный режим хранится в `PLUGIN_DATA/modes/<safe-session-id>.json`; существующие
значения `override: 0` и `override: 1` сохраняются. `LNT1` включает режим
после `LNT0`. Автоматического выбора по модели нет.

## Первая установка

Найди фактическое имя в поле `name` нужного `marketplace.json`. Личный
marketplace из `~/.agents/plugins/marketplace.json` обнаруживается автоматически:
для него `marketplace add` не нужен, даже если его нет в списке. Если другой
источник ещё не подключён, добавь предоставленный локальный путь или Git URL.
Затем установи пакет:

```bash
codex plugin marketplace list --json
codex plugin marketplace add "<источник>"
codex plugin add "lunatron@<marketplace>" --json
```

Настрой `agents.max_concurrent_threads_per_session` в `config.toml` как указано
в разделе «Требования», не уменьшая уже заданный предел.

Подключи все шесть профилей из состава выше из установленного пакета в каталог
`agents` активного Codex home (обычно `~/.codex/agents`).
Используй нового lunatik на каждый простой блок и одного persistent luntik. Профили не
требуют отдельного Fast; не включай Fast у Main.

Если системный промпт входит в заказанную установку или обновление, выполни
[его отдельную инструкцию](system-prompt.md) той же ревизии. Иначе его файл
и настройки не меняй.

Настрой доверие к hooks через штатный Codex app-server. Получи определения
через `hooks/list` и запиши нужный trust через `config/batchWrite` в
`hooks.state`: используй точный ключ hook и его `currentHash` как
`trusted_hash`. Меняй только hooks устанавливаемого плагина; уже доверенные
не переписывай. В том же batch для каждого hook Lunatron — `SessionStart`,
`UserPromptSubmit` — запиши `enabled = true` по его точному ключу.
Не обходи trust и не подставляй хеш из прежней версии.

Если в `<active-codex-home>/AGENTS.md` есть прежний точный блок между маркерами
`LUNATRON_GLOBAL_DELEGATION`, удали этот блок и сохрани остальной текст без
изменений. Не создавай блок заново.

## Проверка после установки

После установки напрямую запусти оба установленных хука с нужными входными
данными на целевой ОС: `SessionStart` и `UserPromptSubmit`. Убедись, что hooks
выполняются без ошибок. На Windows используй Git Bash. Убедись, что прежний блок
`LUNATRON_GLOBAL_DELEGATION` отсутствует. На этом проверка закончена.

Запросы к моделям, пробные задачи, переходы контекста и дополнительные
проверочные процедуры в проверку установки не входят.

## Обновление

Обнови пакет через тот же `codex plugin add
"lunatron@<marketplace>" --json`, затем обнови все шесть packaged profiles из
одной версии. Убедись, что `agents.max_concurrent_threads_per_session` в
`config.toml` не ниже 44; более высокое значение сохрани. Сохрани настройки, данные,
сохранённые результаты, артефакты и остальные плагины. Удали прежний
`agents/lunatron_sol_high.toml` из активного Codex home только если можно
подтвердить, что он не был изменён пользователем и принадлежит прежней
установке Lunatron. Если принадлежность или отсутствие правок установить
нельзя, сохрани файл и запроси решение пользователя.
Профили не требуют отдельного Fast; обычный root режим Main сохраняется.
Через app-server согласуй trust изменённых hook-определений; уже доверенные
не переписывай. Включи оба hook обновлённого Lunatron через их точные
`hooks.state` keys, даже если они были выключены до обновления. Не повторяй bump
source version. Удали прежний точный блок `LUNATRON_GLOBAL_DELEGATION` из
активного Codex home, если он остался, сохранив остальной текст.
Затем выполни раздел проверки для обновлённых частей напрямую.
Полную проверку первой установки без запроса не повторяй.
Новые инструкции загружаются в новой задаче; открытые задачи могут сохранять
прежний контекст.
