# Установка filesystem-search на native Windows 11

## Состав

Плагин сохраняет одно имя и два context hook. На Windows известные файлы
читаются напрямую, текст ищется через `rg -n`, имена — через `rg --files`,
связи кода — внешним Codebase Memory (CBM) MCP, синтаксис — внешним
`ast-grep` MCP. Эти два MCP — отдельные процессы пользовательской установки
Codex; manifest и hooks плагина их не запускают. macOS/Linux используют
прежнюю схему из [`filesystem-search.md`](filesystem-search.md).

## Требования

Используй native Windows 11 и Git Bash по правилам этого репозитория. Нужны
Codex с поддержкой plugins, MCP и hooks, Node.js для существующего hook,
`rg` (ripgrep), `uvx` и сеть для первой загрузки MCP-пакетов. Команды должны
быть доступны активной установке Codex по её штатному `PATH`; не зашивай
машинные пути в plugin config.

Сначала установи, какой именно Codex binary и пользовательский config
обслуживают нужный клиент. Команда `codex` в `PATH` может отличаться от Codex,
встроенного в desktop или VS Code. Проверяй `--help` и доступные CLI-команды у
активной версии. То же правило относится к app-server API: сверяй доступную
схему `hooks/list` и `config/batchWrite`, не предполагай одинаковый интерфейс
у всех версий и не выполняй шаг, которого эта версия не поддерживает.

Проверь в Git Bash, что `rg`, `uvx` и Node доступны (`rg --version`,
`uvx --version`, `node --version`). Если `uvx` отсутствует, установи его по
официальной инструкции `uv`; не подменяй команды PowerShell-обёртками.

## Первая установка

1. Выбери marketplace, уже зарегистрированный в активной установке Codex.
   Проверь список и CLI-синтаксис командами этой версии. Установи тот же
   `filesystem-search` штатным `codex plugin add
   "filesystem-search@<marketplace>"`, используя именно активный бинарник.
   Не подключай marketplace повторно и не создавай второй экземпляр плагина.

2. До регистрации проверь записи MCP `codebase-memory-mcp` и `ast-grep` в
   активном config. Не добавляй одноимённые дубли. Если записи уже есть,
   проверь их команды; исправляй только запись активного config при её
   несовпадении с этой схемой, сохраняя остальные настройки.

3. Настрой CBM в пользовательской конфигурации самого сервера и проверь
   установленный пакет:

   ```bash
   uvx --from codebase-memory-mcp codebase-memory-mcp --version
   uvx --from codebase-memory-mcp codebase-memory-mcp config set auto_index true
   uvx --from codebase-memory-mcp codebase-memory-mcp config get auto_index
   ```

   Последняя команда должна вернуть `true`. Обычный поиск не требует отдельного
   `index_repository`; если его явно вызывают, передают `persistence: false`.
   Граф CBM хранится в пользовательском кэше, обычно
   `~/.cache/codebase-memory-mcp`; плагин не создаёт проектный
   `.codebase-memory/graph.db.zst`. `ast-grep` не нужен постоянный текстовый
   индекс.

4. Обрабатывай серверы независимо. Для уже существующей записи проверь команду
   и исправь только её запись, если она не соответствует схеме; отсутствующий
   сервер добавь только соответствующей командой ниже. Не повторяй команду
   регистрации для уже существующего сервера. Команды — точные для `codex`; если
   активен другой executable, передай ему те же аргументы:

   ```bash
   codex mcp add codebase-memory-mcp -- uvx --from codebase-memory-mcp codebase-memory-mcp
   codex mcp add ast-grep -- uvx --from git+https://github.com/ast-grep/ast-grep-mcp@149e20d47bb7125fb0c1451feea2f48a98742034 --with ast-grep-cli ast-grep-server
   ```

   ast-grep закреплён на неизменяемом commit, а `--with ast-grep-cli` даёт
   серверу исполняемый `ast-grep`. Не заменяй commit плавающим `HEAD`.
   Первая установка требует сети. `UV_OFFLINE=1` — только необязательная
   настройка конкретного сервера после полного прогрева pinned uvx-пакета,
   включая `ast-grep-cli`; не добавляй её в общую настройку или начальную
   команду.

5. Перезапусти Codex. Через app-server получи текущие определения hooks
   командой `hooks/list`, затем доверь и включи оба hook плагина через
   `config/batchWrite`, используя текущие hash из ответа. Hash не копируй из
   этой инструкции и не выдумывай. Сохрани остальные настройки.

   На одной проверенной Windows VDI с тёплым кэшем initialize занял 7,561 с у
   CBM 0.11.0 и 6,892 с у ast-grep с `ast-grep-cli` 0.45.3. Там были заданы
   top-level `mcp_optional_startup_grace_ms = 0` и `startup_timeout_sec = 30`
   для каждого из `[mcp_servers.codebase-memory-mcp]` и
   `[mcp_servers.ast-grep]`. Это пример и измерение той машины, а не
   универсальное требование или доказательство исправления CBM. Несмотря на
   эти значения, позднее для CBM снова наблюдали
   `connection closed: initialize response`. Если сервер повторяемо не
   запускается, проверь stderr и конкретные условия его запуска; запись в
   `mcp list`, ручной `uvx` initialize и эти timeout сами по себе не доказывают
   работу вызова из Codex.

6. Удали старую запись `tgrep` из активного Windows Codex config только если
   подтвердил, что она принадлежит именно прежней установке
   `filesystem-search` на этой Windows-машине. При неясном владельце оставь её
   и сообщи о конфликте; пользовательские кэши, runtime-файлы и данные проектов
   не удаляй.

   Удаляй прежний управляемый блок только из активного
   `<active-codex-home>/AGENTS.md` и только при единственной полной паре
   маркеров `<!-- BEGIN FILESYSTEM_SEARCH_GLOBAL_ROUTING -->` и
   `<!-- END FILESYSTEM_SEARCH_GLOBAL_ROUTING -->`. При отсутствующей,
   неполной или повторной границе останови только это удаление и сообщи о
   конфликте. Остальной `AGENTS.md` сохраняй.

## Проверка после установки

В активной установке проверь список plugin и обе записи MCP, значение
`auto_index`, app-server hook definitions, их актуальные hash, trust и
enabled-состояние. Список MCP подтверждает только регистрацию. Затем создай
одну новую задачу Codex из корня проверяемого проекта и передай ей этот промпт:

> Проведи проверку filesystem-search в текущем проекте в рамках этой задачи.
> Реально вызови `rg -n` для выбранного текста и `rg --files` для выбранного
> имени файла. Реально вызови Codebase Memory MCP `search_graph` по символу из
> проекта и подтверди одну найденную связь через `trace_path` либо ограниченный
> graph query. Реально вызови ast-grep MCP `find_code` с подходящим для проекта
> структурным шаблоном. Отдельно сообщи, если handshake или конкретный вызов
> MCP не удался; не выводи граф или AST из результатов `rg`. Проверь, что в
> контексте этой задачи получен filesystem-search SessionStart routing, а при
> создании субагента ему доставлен SubagentStart routing. Сообщи, появился ли
> в корне проекта новый `.codebase-memory/graph.db.zst`. Для свежих, полных или
> отрицательных выводов сверь текущие файлы и границы поиска, включая hidden и
> ignored пути, если они существенны.

Результат другой ОС, manifest, `mcp list` или ручной `uvx` initialize не
заменяют реальные вызовы из этой новой Codex-задачи. Не объявляй Windows-маршрут
готовым, пока каждый требуемый вызов не выполнен из Codex. Если маршрут
недоступен, назови его и подтверждённое условие сбоя; не выдавай конфигурацию за
runtime-проверку.

## Обновление

Обнови `filesystem-search` штатной командой `codex plugin add
"filesystem-search@<marketplace>"` из той же выбранной записи marketplace.
Для активной установки используй её фактический binary; Git marketplace
обновляй штатной командой только если это поддерживает его версия Codex.
Проверь существующие MCP-записи и не создавай дубли. Сохрани их pinned-команды,
пользовательскую настройку CBM `auto_index`, cache, прочие настройки и секреты.
После обновления перезапусти Codex, снова получи текущие определения/hash hooks
через app-server `hooks/list`, при необходимости обнови trust через
`config/batchWrite` и проверь оба hook. Повтори только изменившиеся runtime
вызовы из раздела проверки; не делай вывод по manifest или наличию MCP-записи.
