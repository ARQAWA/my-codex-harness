# Lunatron: snapshot концепта перед релизом 24 сентября 2026

Этот снимок фиксирует **согласованный результат**, с которым после установки
сверяется работа новой задачи. Основание — обсуждение Lunatron на этом хосте с
5 по 24 сентября, финальный [утверждённый план](codex://threads/01a0c9ed-b658-7ac2-9142-4237f87dff8d)
от 24 сентября и подготовленные исходники. Прежние предложения ниже не являются
действующими правилами. Снимок составлен до выпуска и до пробного запуска;
фактическая работа новой версии здесь не утверждается.

## Задача и принятый принцип

Главная цель — сохранить контекст Main свободным от нового рабочего шума:
больших чтений, логов, промежуточных ошибок и механической реализации. Вторая
цель — отдавать подходящую простую работу более дешёвой по условиям владельца
Luna. Main остаётся владельцем всей задачи: понимает запрос, принимает
существенные решения, готовит поручения, читает решающие оригиналы, принимает
результат и отвечает пользователю. Полный fork наследует доступную историю,
поэтому изолирует **новый** шум, но не очищает уже накопленный контекст.
Экономия времени и токенов этой схемой пока не измерена.

Историческая причина перемены: постоянный исполнитель и широкий поиск через
Luntik добавляли задержки и лишние передачи работы. Одно связное поручение по
готовому плану оказалось более подходящей единицей делегирования. Общий
перехват больших результатов и обязательный reviewer впоследствии убраны;
узкое смысловое чтение и явно вызываемое слепое ревью сохранены.

## Действующий контракт

1. Lunatron по умолчанию выключен. `LNT1` вручную включает режим текущей
   задачи, `LNT0` выключает и требует закрыть её помощников. Установка плагина
   и включение всех трёх его hooks сами режим не включают. Tritron с Lunatron
   одновременно не работают.
2. Main сам делает планирование, обычный поиск и небольшие чтения. Он читает
   обязательные инструкции и решающие исходные фрагменты. Помощникам передаёт
   связные шумные блоки, не всю задачу и не полномочие принять результат.
3. Для **каждого простого или механического блока** Main составляет короткий,
   но законченный мини-план: результат и границы, выбранное решение и точные
   ориентиры, действия и зависимости, разрешённые проверки и условие возврата.
   Затем запускает новый полный fork `agent_type=lunatik` на
   `gpt-6-luna/medium`. Лунатик сам доводит свой блок до результата и решает
   рутинные проблемы в данных границах. Возвращает блокировку только если
   отсутствует необходимое решение или полномочие либо нет безопасного
   разрешённого пути. При неизвестном результате изменения сначала
   устанавливает состояние. Main принимает результат и штатно закрывает fork;
   следующий блок получает нового Лунатика.
4. Для **сложного шумного блока** используется отдельный полный fork. При Main
   Luna или Sol он получает точно ту же модель и reasoning; при Main Astra —
   `gpt-6-sol` с тем же reasoning. Наследование допустимо только если сохраняет
   оба параметра; иначе оба задаются явно. Для Astra оба задаются всегда.
   Если штатный `default` переопределён и мешает контракту, допустим
   встроенный `worker` при том же полном fork и точных параметрах. Невозможность
   сохранить параметры сообщается как несовместимость, без молчаливой замены.
   Fork выполняет весь порученный блок, возвращает короткий итог и указатели на
   основания; Main принимает результат и закрывает его.
5. Один постоянный `luntik` на `gpt-6-luna/xhigh` отвечает только на один
   смысловой вопрос к уже выбранным Main большим данным. Он не выбирает
   источники, не ведёт Discovery, обычный поиск, диагноз или стратегию.
   `capture.cjs` сохраняет ожидаемо большой вывод, `context.cjs` извлекает
   точные диапазоны, совпадения или поля. Main открывает решающие оригиналы.
6. Если независимой нужной работы нет, Main ждёт событие завершения fork до
   20 минут за вызов в пределах доступного инструмента, без частого polling.
   Истечение ожидания само по себе не означает провал. Main не запускает
   обязательного reviewer; Spotty работает лишь по явному выбору skill.
7. Делегирование не расширяет разрешение на тесты, запуск приложения или иные
   эмпирические проверки. Их включают в мини-план только по прямому заказу
   пользователя либо по обязательной принятой процедуре. Новые router, daemon,
   управляющий агент, каталог моделей, MCP и дополнительное состояние не нужны.

## Смежные изменения Scope Focus

`working-standards` переносит полный актуальный набор общих рабочих правил в
skill с описанием для нативного неявного выбора до планирования и выполнения.
Системный промпт остаётся полным и самостоятельным, без ссылки на skill.
Нативный автовыбор skill не гарантирован на каждом ходе. `notebook-cleanup`
вызывается явно и удаляет только весь notebook текущей сессии после точной
проверки `session_id`, пути и состава. Другие сессии и файлы не затрагиваются.

## План реализации и сверки

Утверждённый план реализован в исходниках: контракт и проверка схем fork —
[`lunatron.cjs`](plugins/lunatron/hooks/lunatron.cjs), модель и самостоятельность
простого исполнителя — [`lunatik.toml`](plugins/lunatron/agents/lunatik.toml),
согласованная история решений — [`LUNATRON-DESIGN.md`](LUNATRON-DESIGN.md),
подключение — [`install-instructions/lunatron.md`](install-instructions/lunatron.md).
В Scope Focus добавлены [`working-standards`](plugins/scope-focus/skills/working-standards/SKILL.md)
и [`notebook-cleanup`](plugins/scope-focus/skills/notebook-cleanup/SKILL.md),
уточнён [`task-notebook`](plugins/scope-focus/skills/task-notebook/SKILL.md)
и [инструкция установки](install-instructions/scope-focus.md). Версии, commit,
push и установка выполняются отдельным этапом после этого снимка.

После релиза один короткий синтетический запуск с Main `gpt-6-sol/low` может
наблюдать ручное `LNT1`, готовый мини-план, полный свежий Lunatik Medium для
простого блока, полный Sol Low fork для сложного блока, узкий Luntik при
нужном большом источнике, событийное ожидание, приёмку Main и закрытие fork.
Проверять надо фактический trace и результат, а не только слова Main. Один
такой запуск **не проверяет runtime ветви Main Luna и Astra** и не доказывает
измеренную экономию или автовыбор skill на каждом ходе. Их контракт можно
сверить по исходникам либо отдельно запустить на соответствующих Main.

Исторические альтернативы, заменённые этим решением: постоянный Lunatik,
шесть профилей и Jev-маршрутизатор, Astra-fork для сложной работы Astra Main,
всегда Sol Low для сложной работы независимо от Main, широкий Luntik,
автоматический model gate, общий `PostToolUse`-перехват и обязательный reviewer.
